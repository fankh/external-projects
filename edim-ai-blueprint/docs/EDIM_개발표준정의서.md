## 1. 공통 원칙

1. **API-First** — 모든 화면은 공개 API만 사용. 내부 전용 API 금지 (Toolbox 사용자 UI가 동일 API 호출)
2. **승인 게이트 준수** — Set-up 자산 쓰기는 `approval_status=DRAFT`로만 저장, `APPROVED` 전이는 Approval Service 경유. 우회 코드 금지
3. **모듈 경계** — 모듈러 모놀리스: 도메인 간 직접 DB 접근 금지, 모듈 공개 인터페이스(서비스 계층)만 호출. 경계를 지켜야 MSA 전환 가능
4. **테넌트 필수** — 모든 조회·쓰기에 `tenant_id` 조건. 누락은 리뷰 반려 사유 (RLS 이중 방어)
   - **DB 밖의 이름 공간도 테넌트로 가른다** (18.57). 객체 저장소 키·파일 경로·캐시 키·외부
     식별자처럼 DB 조건이 닿지 않는 자원은, 모든 쿼리에 `tenant_id` 를 붙여도 격리되지 않는다.
     식별자 재료(프로젝트 번호·문서 번호 등)가 **테넌트별 유니크라면 전역에서는 중복이므로**
     키에 테넌트 성분이 없으면 두 테넌트가 같은 키를 만든다. 테넌트 조건으로 조회하는 중복
     가드는 이 충돌을 **원리상 볼 수 없다** — 검사를 얹지 말고 이름 공간을 갈라라.
   - 이름 공간을 바꿀 때 **기존 자원은 저장된 경로를 그대로 쓰게** 두면 데이터 이행이 필요
     없다. 대신 옛 경로를 함께 조회하지 않으면 (1) 갱신이 새 행을 만들고 (2) 옛 경로를 노린
     쓰기를 기존 가드가 놓친다 — 신·구 두 후보를 함께 본다.
   - **권한 범위와 대상 범위를 같이 본다** (18.63). 테넌트 권한으로 실행하는 유지보수·일괄
     동작(GC·재색인·일괄 정리)이 공유 자원 **전체**를 대상으로 삼으면, 권한은 테넌트 안에서
     정당한데 영향은 테넌트를 넘는다. 대상 집합에도 테넌트 조건을 건다. 소유를 판별할 단서가
     없는 옛 자원은 **없는 근거로 지우지도 남기지도 말고** 종전 동작을 유지한 뒤, 제외한
     건수를 응답에 드러낸다.
5. **설정은 환경변수** — 코드에 환경별 분기·시크릿 하드코딩 금지 (`.env.example` 갱신 의무)
6. **결정 기록** — 아키텍처 결정은 ADR(`docs/adr/NNN-제목.md`)로 남긴다 (컨텍스트→결정→결과)

## 3. API 설계 규약

컴포넌트정의서 §4의 계약을 코드 수준으로 구체화한다.

- **버전**: `/api/v1` 경로 프리픽스. 하위 호환 깨는 변경은 v2 신설 (필드 추가는 non-breaking)
- **메서드**: 조회 GET / 생성 POST / 전체 교체 PUT / 부분 수정 PATCH / 삭제 DELETE. 동작형 엔드포인트는 `:action` 또는 하위 리소스 (`.../runs`, `.../finalize`)
- **페이지네이션**: 커서 방식 — `?cursor=&limit=` 요청, `{ items, nextCursor }` 응답. offset 금지
- **오류**: RFC 9457 Problem Details — `{ type, title, status, detail, instance, errors? }`. 도메인 오류코드는 `type` URI 말미에 (`.../errors/duplicate-main-code`)
- **비동기 잡** (EDIM Run·AI·변환): `POST → 202 + { runId }` → `GET .../runs/{runId}` 폴링 + 완료 알림(SSE). 동기 API에 장시간 작업 금지 (>5s)
- **멱등성**: 생성 계열은 `Idempotency-Key` 헤더 지원 (재시도 안전)
- **일시**: ISO 8601 UTC (`2026-07-07T03:00:00Z`), 금액: 문자열 아닌 number + `currency` 필드 분리
- **OpenAPI**: 스키마 자동 생성 필수 — 스펙과 코드 불일치 금지. 인터페이스 정의서는 OpenAPI를 원천으로 발행

## 4. 프론트엔드 표준 — React + TypeScript

### 구조·명명 (프로토타입 관례 승계)

```
src/
  api/        # API 클라이언트 — camelCase.ts (예: blueprintApiClient.ts)
  components/ # PascalCase.tsx — 1파일 1컴포넌트
  hooks/      # use*.ts
  types/      # 도메인 타입 — DrawingDocument 등 백엔드 스키마와 1:1
  pages/      # 라우트 단위 (본 개발 시)
```

- TypeScript **strict 모드**, `any` 금지 (불가피 시 `// oxlint-disable` + 사유)
- 컴포넌트: 함수형 + hooks만. props 인터페이스는 `<컴포넌트명>Props`
- 상태: 서버 상태는 쿼리 라이브러리(TanStack Query 잠정), 전역 UI 상태 최소화
- API 호출은 `api/` 클라이언트 경유만 — 컴포넌트에서 `fetch` 직접 호출 금지
- 스타일: 디자인 토큰(색·간격) 변수화. EDIM 팔레트: primary `#1a1a40`, accent `#2e8b57`
- **동적 Form 렌더러** 주의: `tbx_ui_form.layout_def` 해석 시 스크립트 실행 금지 (선언적 바인딩만) — 보안 결정 (컴포넌트정의서 §11-3)
- **i18n (KO+EN/JA/ZH — REQ-N-015 확정)**:
  - 표시 문자열은 리소스 키(`domain.screen.key`)만 — 하드코딩 금지 (프로토타입 예외)
  - locale 결정: 사용자 설정 > 테넌트 기본 > `Accept-Language`, 번역 누락은 **KO 폴백** (빈 화면 금지)
  - 데이터 라벨은 `GET /i18n/{locale}` 번들 (sys_translation) — 코드 값은 영문 고정, 라벨만 번역
  - 날짜·숫자·통화는 `Intl` 로케일 포맷 (JA 통화 ¥, ZH 千단위 등) — 수기 포맷 금지
  - CJK 폰트 스택: `Pretendard JP/Variable → Noto Sans JP → Noto Sans SC → sans-serif` (로케일별 서브셋 로드)
  - 레이아웃은 EN 기준 +30% 텍스트 확장 허용 (버튼·그리드 헤더 말줄임 규칙)
- 린트: **oxlint** (`react/rules-of-hooks: error` 유지) + prettier. CI에서 강제

### 도면 캔버스 성능

- 5,000 엔티티까지 SVG, 초과 시 Canvas/WebGL 전환 검토 (REQ-N-004)
- 렌더 루프에서 상태 갱신 금지, 팬줌은 transform만 변경 (프로토타입 `usePanZoom` 패턴)

## 5. 백엔드 표준 — Python + FastAPI (잠정)

> 백엔드 언어 확정 시 본 절만 개정. 구조 원칙(계층·경계)은 언어 무관 유지.

### 구조 (프로토타입 승계 + 도메인 확장)

```
app/
  main.py              # 앱 조립만
  config.py            # pydantic-settings — 환경변수 단일 창구
  <domain>/            # code / drawing / cpq / cost / erp ... (모듈 경계)
    router.py          # HTTP 계층 — 검증·직렬화만, 로직 금지
    service.py         # 유스케이스 — 트랜잭션 경계
    repository.py      # DB 접근 — 이 파일 밖에서 SQL 금지
    schemas.py         # pydantic 모델 (JSON camelCase 필드)
```

- **계층 규칙**: router → service → repository 단방향. 타 도메인은 service 인터페이스만 호출
- 타입 힌트 필수 (mypy/pyright 통과), 포맷·린트: **ruff** (format + check)
- pydantic 필드는 camelCase 직접 선언 (프로토타입 관례: `entityType`) — DB snake_case와의 변환은 repository 계층
- 트랜잭션: service 메서드 단위. 승인 전이(approval_status)는 반드시 대상 갱신과 동일 트랜잭션
- **Macro 엔진 안전 규칙**: 평가기는 순수 함수·부수효과 금지, 타임아웃·재귀 깊이 제한, `eval()` 금지 (자체 AST 파서만)
- 예외: 도메인 예외 계층 정의 → 핸들러에서 Problem Details 변환. bare `except:` 금지
- 마이그레이션: 도구는 언어 확정과 함께 결정 (Alembic/Flyway). 규칙: 마이그레이션 파일은 불변, 롤백 스크립트 동반, DDL은 마이그레이션으로만

## 6. Git·리뷰 표준

### 브랜치·커밋

- 브랜치: `main`(보호) ← `feature/<기능ID>-<슬러그>` (예: `feature/CODE-009-running-test`), 수정: `fix/...`
- 커밋 메시지: `<type>(<scope>): <요약>` — type: feat/fix/refactor/test/docs/chore, scope는 모듈 또는 기능 ID
  - 예: `feat(code): CODE-009 Part List Running Test 검증 API`
  - 본문에는 변경 이유·영향. 이슈/기능 ID 참조
- `main` 직접 push 금지, force-push 금지. 릴리스는 태그 (`v0.1.0`, SemVer)

### PR·리뷰 체크리스트

- PR은 작게 (리뷰 가능 단위, ~400라인 목표), 설명에 기능 ID·테스트 방법 명기
- 승인 1인 이상 + CI 통과 필수. 리뷰 관점:
  1. 테넌트 조건 누락 여부 (§1-4)
  2. 승인 게이트 우회 여부 (§1-2)
  3. 모듈 경계 침범 (타 도메인 repository 직접 호출)
  4. 오류 처리·로그 (PII 노출, §9)
  5. 테스트 동반 여부 (§7)
  6. **선언한 인자를 실제로 쓰는가** (18.59). 받아 놓고 쿼리에 넣지 않은 필터 인자는 문법
     오류도 경고도 내지 않고, 호출자·문서·화면은 걸러진 결과라고 믿는다. `/files` 는
     `project` 를 선언하고 Run 산출물 구간에서 쓰지 않아 **어느 프로젝트를 열든 같은 목록**을
     내려줬다(없는 번호에도). 데이터가 한 건일 때는 정상으로 보이므로 **행이 하나뿐인
     시드에서는 드러나지 않는다** — 필터 인자는 값이 다른 두 건으로 검증한다.
  7. **찾지 못한 참조를 NULL 로 넘기지 않는가** (18.58). `x[0] if x else None` 은 "없으면
     비워 둔다" 로 읽히지만, 실제로는 **성공 응답을 주고 어디에도 속하지 않는 행**을 만든다.
     비워 두는 것이 업무상 의미 있는 상태가 아니라면 거부한다.
  8. **가려진 값으로 계산하지 않는가** (18.69). 표시만 고치면 계산 경로가 남는다. 화면이
     마스킹된 금액을 합산해 서버로 보내면 **틀린 값이 문서·이력으로 기록된다**(원가 열람이
     가려진 사용자가 0K 짜리 발주서를 만든다). 금액·수량 같은 업무 값은 **그 값을 가릴지
     결정하는 쪽(서버)이 직접 집계**하고, 클라이언트가 보낸 값은 신뢰하지 않는다. 근거가 없어
     합계에서 빠진 항목은 응답에 드러낸다.
  9. **화이트리스트를 DB 제약과 같은 목록으로 유지하는가** (18.68). 조회 필터의 허용값이
     `CHECK` 제약보다 좁으면 **실제로 존재하는 값이 '모르는 값'** 이 된다. 목록은 상수 하나로
     두고 제약과 나란히 관리한다(`RUN_TYPES`·`ANOMALY_SOURCES` 방식).
  10. **부재(null)의 뜻을 자리마다 확인했는가** (18.75). 같은 `null` 이 통제로 가려짐·값
     없음·해당 없음 중 무엇인지는 자리마다 다르다. 공용 포맷터로 모으는 리팩터링은 값의
     표현만이 아니라 **부재의 의미까지 통일해 버린다** — 실제로 '재고 충족이라 단가 미조회'
     자리에 '가려짐' 기호를 찍는 회귀를 냈다. 모으기 전에 호출 지점마다 그 답을 적고,
     구분이 필요하면 뜻을 아는 필드(`stockOk`)나 `maskMode` 로 분기한다.
  11. **가려진 값을 숫자처럼 찍지 않는가** (18.65). 서버가 통제로 가린 값은 `null` 또는
     자릿수 표기 문자열로 온다. 화면에서 `v ?? 0` 으로 받으면 **₩0** 이 되어 '통제로 가려짐'
     이 '실제로 0원' 과 구분되지 않는다 — 서버 통제가 완전해도 사용자는 잘못된 사실을 믿는다.
     금액은 공용 포맷터(`lib/money.ts`)로만 찍고, **가려진 값이 섞인 합계는 내지 않는다**
     (0으로 치고 더하면 실제보다 작은 총액이 사실처럼 표시된다).
  12. **집계·대시보드 경로도 같은 통제를 지나는가** (18.66). 상세 조회에는 마스킹을 걸어 두고
     같은 수치를 모아 보여주는 경로를 빠뜨리면 통제가 무의미하다. 특히 `request` 를 받지 않는
     핸들러는 **열람 모드를 물어볼 수단 자체가 없어** 조용히 통제 밖에 있게 된다.
  13. **자리표시자 값을 화면에 남기지 않는가** (18.67). '모듈 구축 전 고정값' 같은 하드코딩은
     기능이 생긴 뒤에도 남아 **지어낸 숫자가 실적처럼** 보인다. 0 을 보이는 것보다 나쁘다.
  14. **검증이 구현의 규칙을 베끼지 않는가** (18.81). 선택·판정 규칙을 검증 쪽에 다시 적으면
     구현이 바뀔 때 **검증만 옛 규칙으로 판정해 거짓 실패(또는 거짓 통과)** 를 낸다. 규칙이
     결과에 영향을 주면 **서버가 그 근거를 응답에 밝히고**(어느 Run·어느 기준을 썼는지),
     검증은 그 값을 읽어 성질만 확인한다. 근거를 밝히는 것은 사용자에게도 이득이다.
  15. **빈 값과 모르는 값을 구분하는가** (18.62). `if v in ("A","B"): clause += …` 는 모르는
     값이 오면 **조건을 아예 붙이지 않아 전체를 돌려준다.** 빈 값(=전체 보기)은 의도지만
     모르는 값은 오류다. 둘을 같이 처리하면 **거른 것처럼 보이는 전체 목록**이 나가고,
     그것은 필터가 없는 것보다 나쁘다(호출자가 걸러졌다고 믿는다). 모르는 값은 422 로 알린다.
     같은 이유로, 찾지 못한 기준값으로 스코프를 계산해 그럴듯한 결과를 만들지 않는다.

## 7. 테스트 표준

| 계층 | 도구(잠정) | 기준 |
|---|---|---|
| 단위 | pytest / vitest | service·엔진 로직. 신규 코드 커버리지 **80%** 목표 (엔진류 90%) |
| 통합 | pytest + testcontainers | repository·API 계약 (실 DB) |
| E2E | Playwright | 핵심 여정: 코드 등록→Running Test→CPQ→Run→견적 (개요 §7) |
| 성능 | k6 (잠정) | REQ-N-001~005 — Run 1시간/BOM 30초/응답 2·3초 |

- **'실행하지 않음' 을 '통과' 로 읽지 않는다** (18.64). 검증 도구가 시작조차 못 한 경우
  (락 충돌·환경 미비·전제 실패)는 **성공과 반드시 다른 신호**로 끝나야 하고, 부르는 쪽도
  그 신호를 실제로 읽어야 한다. 락처럼 프로세스에 매인 자원은 **소유자 생존을 확인**해
  회수하고(강제 종료 시 정리 코드는 돌지 않는다), 회수했다는 사실을 출력한다.
  파이프로 연결해 부르면 **마지막 명령의 종료코드**를 보게 된다 — 검증 실행은 출력을 파일로
  받고 종료코드를 따로 확인한다.
- 테스트 명명: `test_<대상>_<조건>_<기대>` / `it('...조건이면 ...한다')`
- **Macro 엔진은 golden test**: 수식·입력·기대값 테이블 기반 회귀 (특허 검토로 문법 변경 가능성 대비)
- BOM 전개·순환 검증은 경계 케이스 필수 (깊이 제한·순환·빈 관계)
- 테스트 데이터: 발표자료 예시 코드 체계(KDCR 3-13, KAD-450-…) 사용 — 문서와 대조 가능

## 응답 정직성 규약 (2026-07-25, 9.79·9.81 실측 결함에서 도출)

"조회하지 않음"·"판단하지 못함"을 **"이상 없음"으로 답하지 않는다.** 사용자는 이를 검증 결과로 읽는다.

| 금지 패턴 | 왜 위험한가 | 대신 |
|---|---|---|
| 상한 초과분을 조용히 버림 | '조회 안 한 항목'이 '없는 항목'으로 오표시 (9.79 `/codes/drawing-files`) | `truncated` 개수를 응답에 넣고, 클라이언트는 청크로 나눠 전량 조회 |
| 대상 부재 시 빈 결과 + `ok: true` | '점검 못 함'이 '정상'으로 오표시 (9.81 `error-check`) | `found` 를 별도 필드로, `ok` 는 **실제 점검해서 위반 0** 일 때만 참 |
| 판정 불가를 위반/정상 한쪽에 편입 | 경고 남발 또는 위험 은폐 | `unevaluated` 로 분리하고 사유(값 미정·구문 불가) 병기 |
| 점검 결과를 **계산 없이 고정값으로** 반환 | 점검한 적이 없는데 통과로 읽힘 (10.9 Running Test `passed:true, cycleCheck:"OK"` 고정) | 실제로 계산해서 채운다. 계산하지 않을 거면 그 필드를 **두지 않는다** |
| 재귀 전개에서 순환·깊이 초과분을 조용히 버림 | 무한 재귀는 막히지만 **일부만 전개된 결과가 전량으로 보임** → 원가·소요량이 말없이 적게 집계 (10.9 BOM) | 버린 간선·상한 도달 여부를 응답에 고지하고, 후속 조치(승인 등)를 그 상태에서 진행시키지 않는다 |
| 원인이 다른 실패를 같은 오류로 뭉뚱그림 | '승인 하위 없음'이 '코드 없음(404)'으로 오표시 (11.0) | 원인별로 상태 코드·문구를 나눈다. 정상 응답 + 사유 고지로 풀 수 있으면 오류로 만들지 않는다 |
| 목록에 식별자를 빼고 내려줌 | 화면이 보여 주기만 하고 **아무 조치도 할 수 없다** (11.1 Where-Used `relId` 누락 — 잘못 건 DRAFT 관계 회수 불가) | 행 단위 조치가 가능한 목록은 식별자를 함께 내려준다 |

**점검 방법**: 신규 조회 API 는 ①대상이 없을 때 ②상한을 넘길 때 ③판정 불가 입력일 때
세 경우를 각각 호출해 보고, 응답만 보고도 상태를 구분할 수 있는지 확인한다.
UI 는 그 세 상태를 서로 다른 문구로 표시한다(같은 '없음'으로 뭉뚱그리지 않는다).

**통제는 경로 단위가 아니라 데이터 단위로 건다**: 열람·다운로드 제한을 추가할 때는 같은
데이터에 닿는 **모든 경로**를 세어 본다 — 조회 API·렌더 PDF·산출물 파일·export·목록.
한 곳만 막으면 통제가 아니라 장식이다. 실제로 세 번 반복됐다: 8.3(마스킹이 19개 민감 조회 중
3곳에만) · 11.6(원가 근거가 PCR 에만, 견적 확정은 그대로 통과) · 15.1(다운로드 통제가
렌더 경로에만, 산출물 파일은 무방비). 통제를 넣은 뒤에는 **막힌 경로와 뚫린 경로를 함께
검증**한다(차단 403 + 권한자 200) — 과잉 차단도 결함이다.

**차단 단위도 데이터 단위로**: 한 반출물에 여러 정보그룹이 섞이면(단가 대장 = 단가 + 공급처명)
파일 단위로 막지 말고 **해당 열·테이블만** 가린다. 파일을 통째로 막으면 다른 그룹에 대한
정당한 권한까지 빼앗는다(15.8 — 단가 열람만 부여받은 사용자의 반출이 공급처명 때문에 막혔다).
선택 기준: 내용 전부가 통제 대상이면 차단, 섞여 있으면 열 마스킹·항목 제외 + **뺀 사실 고지**.

**잠금 토큰은 모든 쓰기 경로에서 올린다**: 낙관적 잠금(version·updated_at)을 도입하면
그 데이터를 바꾸는 **쓰기 경로를 전수로 세어** 전부에서 토큰을 올린다. 하나라도 빠지면
그 경로의 변경이 잠금에 보이지 않아 조용히 덮어써진다 — 잠금이 걸려 있다는 착각이 무방비보다
나쁘다(16.7 — 매크로 잠금을 걸었는데 치수 저장 경로가 version 을 올리지 않아 무력화됐다).
회귀는 '차단되는가' 가 아니라 **'다른 경로의 변경이 잠금에 보이는가'** 로 짠다.

**상한을 두면 절단을 알린다**: 목록·조회에 LIMIT 을 걸면 잘렸다는 사실을 응답에 남긴다
(객체형은 본문 `truncated`, 목록형은 `X-Truncated` 헤더). 특히 **두 수치를 대조하는 화면이
있으면 그 목록은 완전성이 판단에 쓰인다** — '최근 N건이니 괜찮다' 는 사람의 판단보다
실제로 대조되는지가 기준이다(16.9 — Run 목록 1000 vs 통계 491+524 로 실제 불일치가 났다).
호출자가 limit 을 명시해 요청하는 위젯은 조용한 절단이 아니므로 대상 밖이다.

**통제는 저장 여부가 아니라 데이터에 건다**: 미리보기·즉석 렌더처럼 영속되지 않는 출력도
담긴 데이터가 같으면 같은 통제를 받는다. "저장하지 않으니 대상이 아니다" 는 판단이 실제로
견적 단가·합계를 무통제로 내보냈다(17.10). 새 출력 경로를 만들 때는 담기는 데이터의
정보그룹을 먼저 정한다.

**통제 적용 여부를 스캔할 때는 헬퍼 이름을 전수로 먼저 뽑는다**: 아는 헬퍼만으로 훑으면
**통제가 있는 곳을 없다고 분류**한다 — 17.10 에서 `_assert_downloadable` 을 목록에 넣지
않아 거래처 대장 반출을 '통제 없음' 으로 잘못 읽었다. 잘못된 '없음' 은 잘못된 '있음' 만큼
위험하다(고쳐야 할 곳을 못 보게 하거나, 이미 된 곳을 또 건드리게 한다).

**오류는 고칠 수 있는 말로 돌려주고, 원문은 서버에 남긴다**: DB 예외 문구를 그대로 내보내면
제약명·테이블 같은 내부 구조가 새고, 동시에 **사용자는 무엇을 고쳐야 할지 알 수 없다**
— 두 손해가 함께 온다. 알려진 실패는 분류해 행동 가능한 문장으로 바꾸고, 분류되지 않으면
"내부 오류" 로 답하되 **원문은 구조화 로그로 남긴다**(가린다는 이유로 정보를 없애면 다음에
원인을 못 찾는다). 사용자가 입력한 수식·표현식에 대한 파서 메시지는 예외다 — 그건 사용자의
입력을 설명하는 것이지 시스템 내부가 아니다(18.27).

**연쇄로 건드리면 건드린 범위를 알린다**: 한 요청이 다른 테이블 행까지 지우거나 연결을
끊으면, 무엇을 얼마나 건드렸는지 **응답과 이력에 함께** 남긴다. 대상 하나만 지운 줄 아는
사용자는 이후 자료가 비는 이유를 찾지 못한다(18.21 — 도면 삭제가 자식 6곳을 건드리는데
응답은 도면번호뿐이었다). 지우지 않고 연결만 끊는 것은 이름을 구분한다(`filesDetached`).

**정적 게이트가 볼 수 있게 쓴다**: 테이블명을 변수로 조립하면(`f"DELETE FROM {tbl}"`)
그 문장은 정적 검사에서 **사라진다**. 기준선에 예외로 남는 것보다 나쁘다 — 예외는 기록이라도
남지만, 보이지 않으면 없는 것으로 읽힌다. 반복이 지저분해 보여도 명시적으로 쓴다(18.21).

**서버가 클라이언트의 기존 호출을 무효화하면 클라이언트 대응이 선행돼야 한다**: 새 값을
응답에 담아 "쓰면 된다" 로 만들어도, **쓰지 않는 호출자가 있으면 그건 깨지는 변경**이다.
본인 비밀번호 변경에 세션 무효화를 걸었다가 기존 호출자가 401 을 맞았고, 인증 실패가
연쇄되어 **데모 계정이 잠겼다**(18.54). 서버만 먼저 바꾸지 말고, 남아 있는 호출자를 먼저
확인한다. 보안 개선이 가용성을 깨지 않게 한다(9.96 에서 세운 원칙).

**계정 상태·자격을 바꾸는 조작은 이미 열린 세션에도 반영되는지 확인한다**: 비활성화는 즉시
반영되는데 비밀번호 재설정은 아니었다 — 같은 목적(계정 탈취 대응)인데 한쪽만 동작하면
통제가 아니다(18.51). 새 조작을 만들 때 "이 조치로 지금 열려 있는 세션이 끊기는가" 를 묻는다.

**규약이 문서에만 있고 구현이 없는지 주기적으로 확인한다**: 표준에 적힌 것은 지켜지고 있다고
가정된다. `Idempotency-Key` 는 §3 에 규정돼 있었으나 **코드에 문자열조차 없었고**, 헤더를
보내도 조용히 무시돼 재시도가 원가를 두 배로 만들었다(18.45). 문서가 "지원" 이라고 말하면
그것을 근거로 판단이 이뤄지므로, **문서의 약속은 구현 여부를 확인해야 할 목록**이다.

**멱등 키는 작업 전에 선점한다**: 작업을 마친 뒤 키를 저장하면 동시에 들어온 두 요청이 둘 다
조회를 빗나가 **둘 다 실행되고**, 충돌은 키 저장 시점에야 드러난다 — 이미 중복이 생긴 뒤다.
먼저 잡고(선점) 작업하며, 처리 중인 키로 다시 오면 409, 완료된 키면 저장된 응답을 돌려준다.

**검사 기능은 '위반 사례로 실제 걸리는지' 로 확인한다**: 통과만 확인하면 **항상 통과하는
규칙도 통과로 보인다**. 설계 검증은 한계 1,500 에 대해 8,100 을 합격으로 냈고, 화면에는
검증이 도는 것처럼 보였으며 경고 문구도 있었다(18.36). 규칙·정책을 데이터로 두는 기능은
엔진 규약(무엇이 통과인가)을 문서화하고, **위반 사례를 만들어 불합격이 나오는지** 밟는다.

**기동 시 실패해도 앱이 뜨는 구조라면 그 결과를 상태로 드러낸다**: 마이그레이션이 롤백돼도
`/health` 가 `ok` 를 돌려주면 **배포가 성공으로 보이고 코드와 스키마가 어긋난 채 운영된다**
— 게다가 검증이 실패하면 제품이 아니라 검증을 의심하게 된다(18.37). 가용성을 위해 계속
띄우는 것은 좋으나, 무엇이 실패했는지는 배포·검증이 판단할 수 있게 노출한다.

**컬럼·제약을 새로 참조하기 전에 스키마를 본다**: 이름도 제약도 기억이 아니라 확인 대상이다. 저장소에
스키마 스냅샷(`docs/ddl/schema_snapshot.json`)이 있으므로 추측할 이유가 없다 — 이 세션에서
세 번 틀렸고(`spec`→`specification`, `grade`→`management_grade`, 없는 `total_amount`)
마지막 것은 **운영 500** 까지 갔다(18.34).

**아무도 호출하지 않는 경로는 고장 난 채로 있다**: `erp_po` 는 행이 0개였고, 그 lifecycle
엔드포인트는 한 번도 호출된 적이 없어 결함이 드러날 기회가 없었다. **API 표면 커버리지
실측(18.9)에서 미호출로 잡힌 경로는 "안 쓰는 것" 이 아니라 "확인되지 않은 것"** 으로 읽는다.

**주석이 약속한 것이 코드에 있는지 확인한다**: 이 세션에서 같은 형태를 세 번 만났다 —
BOM 관계 삭제 주석은 "원가·소요량이 달라진다" 고 적고 소요량을 안 남겼고, 매크로 저장 주석은
"어떤 식으로 바뀌었는지 남긴다" 면서 새 식만 남겼으며, 치수 저장 주석은 "몇 건이 어떻게
바뀌었는지" 라 해놓고 건수만 남겼다. **주석이 옳게 적혀 있으면 아무도 다시 확인하지 않는다** —
그래서 틀린 주석보다 '옳지만 지켜지지 않은 주석' 이 오래 산다. 리뷰·점검 때 주석을 요구사항으로
읽고 그 값이 실제로 있는지 본다(18.29).

**수정 감사에는 바꾸기 전 값을 담고, 같은 데이터의 다른 경로도 함께 고친다**: 새 값만 남기면
"왜 결과가 달라졌나" 를 되짚을 수 없다. 이전 이력의 `after` 로 거슬러 올라가는 방법은
**같은 데이터를 바꾸는 다른 경로가 있으면 끊긴다**(매크로 수식은 Macro Studio 와 치수 저장
양쪽에서 바뀐다). 한쪽만 고치면 사슬이 이어지지 않는다(18.29).

**삭제 감사에는 지운 값을 담는다**: 삭제는 원본이 사라지는 연산이므로 대상 식별자만 남기면
**무엇이 지워졌는지 어디에서도 복원할 수 없다**. 대부분의 삭제문은 이미 `RETURNING` 으로
값을 읽고 버리므로 추가 비용 없이 `before` 에 넣을 수 있다(18.16). 아울러 **주석이 "무엇이
달라진다" 고 적었으면 그 값이 `before` 에 실제로 있는지 확인한다** — BOM 관계 삭제는
"원가·소요량이 달라진다" 고 적어 놓고 소요량을 남기지 않고 있었다.

**같은 부류를 세 번 고쳤으면 개별 수정을 멈추고 전수로 훑는다**: 같은 결함이 반복해서
나온다는 것은 그 종류가 코드 전체에 퍼져 있다는 뜻이다. 네 번째를 또 그 자리에서 고치면
다섯 번째가 남는다. 기계적으로 후보를 뽑고(정규식·AST), 적용 대상과 **대상 밖인 것의 근거**를
함께 적은 뒤, 공통 헬퍼로 모은다(18.14 — 조용한 절단을 세 번 개별 수정한 뒤 상한이 걸린
51곳을 훑어 3종에 적용하고 나머지는 근거와 함께 제외했다).

**같은 검사를 두 곳에 인라인으로 두지 않는다**: 상한·정규화·형식 검증처럼 어디서나 같아야
하는 검사는 헬퍼로 만들고, 같은 검사를 하는 기존 지점을 찾아 합친다. 인라인으로 흩어 두면
**나중에 추가한 검사가 한쪽에만 붙는다** — 빈 파일 검사가 Excel Import 에만 있어 0바이트
첨부가 그대로 등록됐다(17.12). 아울러 **틀린 안내는 없는 안내보다 나쁘다**: 나눌 수 없는
바이너리에 "시트를 나눠 올리십시오" 를 띄우면 사용자가 그대로 시도한다.

**결정성은 깨질 조건을 일부러 만들어 확인한다**: "같은 입력이면 같은 결과" 를 두 번 연달아
호출해 보는 것으로는 증명되지 않는다 — 시각처럼 **granularity 가 있는 값이 섞여 있으면 그
안에서는 일치**하므로 검증이 운으로 통과한다(18.10 — DXF 지문에 생성 시각이 들어 있었고,
같은 초 안에서는 같아서 부하가 걸린 플릿에서만 실패했다). 지문·비교를 만들 때는 포맷이
시각·GUID·핸들 같은 값을 심는지 먼저 확인하고 제외한다.

**커버리지는 실행을 세고, 못 잰 것은 낮은 값으로 보고하지 않는다**: 검증 소스의 경로
문자열을 세면 동적으로 조립한 URL 을 놓치고 주석·상수의 경로를 실행된 것으로 착각한다 —
두 오차가 서로를 가려 수치가 그럴듯해진다. 실제 요청 로그를 세고, 측정 창이 깨졌으면
(컨테이너 재시작 등) **수치를 내지 않고 실패**한다(18.9).

**'전부·100%' 는 무엇과 무엇 사이의 연결인지 밝힌다**: 커버리지 주장은 고리를 특정하지
않으면 읽는 사람이 사슬 전체로 읽는다. 추적표가 "전 기능이 요구사항에 연결됨(100%)" 이라고
적었을 때 실제로 100% 인 고리는 하나였고, 기능→화면은 55% 였으며 기재된 화면 ID 조차
**103건 중 99건이 코드에 없는 이름**이었다(18.6). 주장하기 전에 **그 연결을 코드에서 실제로
따라가 보고**, 못 이으면 못 이었다고 적는다.

**문서와 구현이 다른 식별자 체계를 쓰면 매핑을 추측하지 않는다**: 이름이 다른 것과 없는 것은
다르다. 유사도로 이어 붙이면 문서는 그럴듯해지고 틀린다 — **그럴듯한 오답은 공백보다
나쁘다**(공백은 물어보게 하지만 오답은 그대로 쓰인다). 체계 통일이나 매핑표 확정은 사람이
정할 결정 사항으로 올린다.

**우연히 안전한 상태를 안전하다고 부르지 않는다**: 통제가 어디에 걸려 있는지 확인하지 않으면
"막혀 있다" 는 사실만 보고 안전하다고 판단한다. `/api/v1` 밖 구형 라우터 5개는 앱 인증이
전혀 없었고 nginx 설정 한 줄이 막고 있었는데 그 사실이 문서에도, 검증에도 없었다(18.6).
바꿀 수 없는 사정이 있으면 통제 방식을 그대로 두더라도 **그 통제가 살아 있다는 것을
불변식으로 고정**한다(설정이 바뀌면 검증이 실패하도록).

**검증 결과에는 그 실행이 깨끗했는지가 함께 붙는다**: 검증 도중에 배포가 나가면 결과는
제품 상태가 아니다 — 실패가 재시작 탓일 수 있고, **반대로 재시작 중 우연히 통과하면
실패했어야 할 실행이 초록으로 보인다**. 후자가 더 위험하다. '중간 배포 없음' 을 사람의
기억에 맡기면 확인되지 않으므로 러너가 직접 확인한다(`/health.proc` 비교 — 다르면 초록도
실패, 읽지 못하면 "확인하지 못했다" 를 명시). 플릿이 도는 동안에는 푸시하지 않는다(18.4).

**실증에는 실증의 조건을 먼저 확인한다**: "재현했다" 는 말은 재현 조건이 실제로 성립했을
때만 쓴다. 17.3 에서 "테넌트 A 가 테넌트 B 의 데이터를 바꿨다" 고 보고했지만, 검증 계정이
어느 테넌트인지 확인하지 않았고 실제로는 **계정도 대상도 같은 테넌트**였다 — 대상만
`tenant_id=2` 로 고르고 계정은 테넌트 1 일 것이라 **가정한 뒤 그 가정을 결론으로 옮겼다**.
교차를 보이려면 양쪽을 모두 확인해야 한다. 확인하지 못했으면 **"코드로 확인(정적)" 과
"실행으로 확인(실증)" 을 구분해 적는다** — 둘을 섞으면 근거의 강도를 잘못 전달한다.

같은 이유로 **검증이 무엇을 증명하는지도 따져야 한다**: '내 목록에 없는 ID' 를 대상으로
쓰면 그 ID 는 존재하지 않는 값일 수 있고, 그러면 "없는 대상은 거절된다" 만 증명된다.
보려는 성질(남의 것은 못 건드린다)을 증명하려면 **대상이 실재하는지부터 확인**한다.

**결정은 대상의 현재 상태를 보고 내린다**: 승인·반려처럼 미결로 대기하는 요청은 그 사이
대상이 바뀔 수 있다. 결정을 반영할 때 대상의 현재 상태를 확인하지 않으면 **그 사이의 변경이
조용히 되돌아간다**(비활성으로 막아 둔 것이 묵은 승인으로 되살아나는 형태). 조건부 UPDATE 로
막는 것만으로는 부족하다 — 0행이 바뀌어도 요청은 '승인' 으로 기록되고 요청자에게 승인
알림이 가면, 아무것도 하지 않고 했다고 답하는 것이다. 승인은 미리 확인해 409 로 거절하고,
반려는 막지 않되(막으면 승인함에서 치울 수 없는 요청이 남는다) **요청을 닫는 것과 자산을
바꾸는 것을 분리**하고 전이 여부를 이력에 남긴다(17.6).

**허용 집합은 DB 에도 둔다**: 상태·구분처럼 값의 집합이 정해진 컬럼은 CHECK 제약을 건다.
집합이 애플리케이션에만 있으면 **잘못된 값이 저장되는 것을 아무도 막지 않고**, 이후
`WHERE status='APPROVED'` 같은 조회가 그 행을 걸러 내므로 **오류가 아니라 실종으로 나타난다**
(승인했는데 목록에 없다). 제약을 새로 걸 때는 코드의 쓰기 경로를 전수로 모아 집합을 정한다 —
하나라도 빠뜨리면 정상 경로가 500 이 된다(17.1 — 상태 컬럼 6개 중 4개에 제약이 없었다).

**문서 생성기도 데이터가 있는 곳을 전부 읽는다**: 코드에서 뽑는 문서는 추출원이 실제
데이터의 일부만 덮으면 **없는 것을 없다고 말하는 대신 통째로 침묵한다** — 빈 칸이 아니라
행 자체가 사라지므로 읽는 사람은 누락을 알아챌 수 없다. 스키마처럼 원본이 여러 곳에
나뉘어 있으면(`base_schema.sql` + alembic 리비전, `CREATE TABLE` + `ALTER TABLE`) 전부
읽는지 확인한다. 아울러 **'미분류' 같은 미완 표시는 별도 게이트로 잡는다** — 생성기와
문서가 똑같이 미분류를 담으면 드리프트 비교는 통과하기 때문이다(17.2 — 핵심 기준 테이블
34개가 문서에서 빠져 있었고, 규칙 공백 21건이 그때 함께 드러났다).

**쓰기에는 이력을 남긴다**: 업무 데이터를 바꾸는 엔드포인트는 `_audit()` 로 행위자·대상·
변경 내용을 기록한다. 개인 설정·읽음 표시처럼 이력 가치가 없는 것만 예외이며, 그 경우
`check_audit_coverage.py` 의 EXEMPT 에 근거와 함께 등록한다. 기록이 없으면 사고·이의 제기
때 "누가 언제 바꿨는가" 에 답할 수 없고, 그 답을 못 하는 시스템은 통제 문서로 쓸 수 없다.

**판정 필드를 둘 때**: `passed`·`ok`·`valid` 같은 필드는 소스에서 **그 값이 계산되는 지점을
짚을 수 있어야** 한다. 리터럴로 채워져 있으면 그 자체가 결함이다(10.9 에서 실제로 발견).
UI 도 마찬가지다 — 서버 판정과 무관하게 "이상 없음" 을 출력하는 고정 문구를 두지 않는다.
