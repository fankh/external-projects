### 1.2 미결 — 착수 회의에서 확정해야 하는 것

§11 의 체크리스트가 전체 목록이다. 그중 **계획 자체를 바꾸는 것**은 셋이다.

1. **EWACS 이력 데이터의 보존 기간** — REQ-2-02(시간대/요일/**계절** 패턴 학습)의 성립 여부가 여기 걸린다(§10 R-2).
2. **오탐률·적중률 정량 목표** — 인수 기준의 «정상 작동 확인»을 무엇으로 판정할지가 정해지지 않았다.
3. **Nexus 접근 권한** — D-1 을 택한 이상 빌드 자체가 불가능하다(§10 R-1).

## 2. Java 결정이 계획을 바꾸는 지점

코드베이스 분석 §7.2 는 「독립 AI 서비스」를 가정하고 재사용 가능성을 적었다. **D-1 로 그 판정이 뒤집힌다** — 프레임워크 재사용이 실제로 가능해지고, 대신 ML 실행 방식이 새 쟁점이 된다.

| SOW 요구 | 독립 Python 서비스였다면 | **Java + cupia-framework (확정)** |
|---|---|---|
| 알림 모듈 (REQ-2-05) | 전량 신규 개발 | **`cupia-notification-service` + `cupia-mail`/`cupia-sms` 재사용.** 오케스트레이션·렌더·수신자 해석·IN_APP 수신함·배달 워커가 이미 있다 |
| 통합 계층 REST/Event Bus/Webhook (REQ-2-08) | 전량 신규 개발 | **`cupia-streams`(봉투·채널·재시도·Outbox) + `cupia-gateway` 재사용** |
| 실시간 대시보드 반영 (REQ-2-09) | 전량 신규 개발 | **`cupia-realtime`(SSE/WS + Redis Pub/Sub 팬아웃 + JWT) 재사용** |
| Admin Console (REQ-2-09) | 자체 React | **`@cupia/ui` 77 컴포넌트 + MFE remote 패턴** — `customs-admin-shell` 에 마운트 |
| 인증·감사·개인정보 | 자체 구현 | `cupia-security` · `cupia-core` 감사 · `cupia-privacy`(HR/근무 데이터를 다루므로 접속기록 의무 발생 가능) |
| 배포 | Docker Compose | Jenkins → Nexus/Harbor → **ArgoCD GitOps** (`customs-deploy`) |
| **시계열 예측·임계치 학습** | Python 생태계 그대로 | **§4.2 의 핵심 쟁점.** Java 로 어떻게 할지 정해야 한다 |
| **전제 조건** | 없음 | **Nexus 접근 권한이 필수** — 없으면 한 줄도 빌드되지 않는다 |

**요약**: 알림·통합·실시간·UI 는 신규 개발에서 **재사용으로 내려간다**(공수 감소). 대신 예측·임계치 학습이 **Java 로 올라온다**(설계 부담 증가). 견적서 2(모듈별 정액 3모듈 33M/126M/61M)의 배분을 이 이동에 맞춰 재확인할 필요가 있다.

## 4. 기술 결정

### 4.1 일반

| 항목 | 결정 | 근거 |
|---|---|---|
| 모듈 경계 강제 | Spring Modulith 검증 테스트 + ArchUnit(`CupiaArchitectureRules` 상속) | 배포를 쪼개지 않고 경계를 지키는 유일한 수단. 위반은 빌드 실패 |
| 배치 | Spring Batch (야간 재학습·집계) | 사내 `tancis-batch-*` 계보. 별도 스케줄러 도입 불필요 |
| 스트리밍 | `cupia-streams` (Kafka 봉투·재시도·Outbox) | 프레임워크 제공. 자체 구현 금지 |
| 이벤트 발행 | **Outbox 패턴** — 트랜잭션과 발행의 원자성 | `cupia-streams` 내장. 알림 유실/중복발송 방지의 근본 |
| LLM 호출 | OpenAI 호환 `/v1/chat/completions` 를 Java HTTP 클라이언트로 직접 호출 | 사내 vLLM 이 이미 OpenAI 호환으로 서빙 중(`sentinel` 선례). 별도 SDK·언어 불필요 |
| 프롬프트 관리 | DB 저장 + 변경 이력 + 롤백 + `change_summary` 필수 | `ai-team/customs-docs` 에서 이미 검증된 패턴을 그대로 답습. 프롬프트를 코드에 박지 않는다 |
| 알림 중복 억제 | `(source, dedupKey)` 상태 전이 기반 — `firing→resolved` 전이에만 발송 + 쿨다운 | `sentinel` DESIGN.md 의 플랩 억제 결정을 답습. 오탐 튜닝(11~12월)의 절반이 여기서 해결된다 |
| Feature Store | PostgreSQL 물화 집계 테이블 | 전용 제품(Feast 등)을 도입할 데이터 규모가 아니다. 요건 설계에서 규모 실측 후 재확인 |

### 4.2 핵심 쟁점 — Java 에서 시계열 예측과 임계치 학습을 어떻게 하나

D-1 의 유일한 실질적 부담이다. 결론은 **「추론은 Java, 필요하면 학습만 오프라인」** 이다.

| 기능 | 방식 | 판단 근거 |
|---|---|---|
| **동적 임계치** (FN-2-02) | 요일 × 시간대 버킷별 **기준선 + 강건 산포(MAD) 기반 분위수 임계치**. 계절 성분은 분해로 분리. 야간 배치 재추정 | 이것은 «학습»이라기보다 **계절 분해 + 통계 추정**이다. 순수 Java 로 충분하고, 설명 가능성이 높아 관세직원 대상 «왜 이 임계치인가» 설명에 유리하다. 학습형 모델보다 오탐 튜닝도 쉽다 |
| **업무량 예측** (FN-2-01) | **Holt-Winters 삼중 지수평활**(일간·주간 이중 계절성) + 예측구간. 초과 전 경고는 예측구간 상한이 임계치를 넘는 시점으로 정의 | 업무량 시계열은 강한 주기성 + 완만한 추세라는, 고전 기법이 가장 잘 듣는 형태다. Apache Commons Math 로 구현 가능 |
| **원인 분석** (FN-2-03) | 기여도 분해(어느 업무 단계·조직·문서유형이 초과에 얼마나 기여했는지) + 상관 분석 + 규칙 | 「병목 업무 자동 진단」은 분류 문제가 아니라 **기여도 귀속 문제**다. 학습 모델이 필요 없다 |
| **LLM 인사이트** (FN-2-04) | vLLM REST 호출 | 언어 무관 |
| **대응 추천** (FN-2-06) | 제약 기반 배분 최적화(인력 가용성·자격·근무 규칙 제약 하의 할당) | 최적화 문제. Java 로 구현하거나 OR 라이브러리 사용 |
| **탈출구** | 위 기법으로 정량 목표를 못 맞추면 → **오프라인(Python)에서 학습 → ONNX 내보내기 → Java ONNX Runtime 추론** | 런타임은 여전히 Java 단일 스택이므로 D-1 과 충돌하지 않는다. 배포·운영 모델이 바뀌지 않는 것이 핵심 |

> **이 판단은 6월 «백테스트 게이트»(§6 Phase 3-G1)에서 실측으로 검증한다.** 고전 기법으로 목표 미달이면 그 시점에 탈출구를 발동한다 — 나중에 발견하지 않도록 게이트를 앞에 둔다.

## 5. EWACS 접근 없이 시작하는 법 — 계약 우선(Contract First)

일정의 유일한 외부 종속은 EWACS 접근이다(SOW 8. 발주자 제공 사항). **접근이 늦어져도 멈추지 않도록** 구조를 이렇게 잡는다.

1. **수집 어댑터를 인터페이스로 먼저 고정한다.** `EwacsMetricSource`, `WorkMetricSource`, `StaffScheduleSource` 등.
2. 구현체를 둘 둔다 — `RealAdapter`(EWACS 직결)와 **`ReplayAdapter`**(합성·익명화 CSV 를 시간축에 따라 재생).
3. **파이프라인 하류 전부**(피처·임계치·예측·RCA·인사이트·추천·알림·UI)는 `ReplayAdapter` 위에서 개발·테스트한다.
4. EWACS 접근이 열리면 **어댑터 한 겹만 교체**한다. 상류 스키마가 예상과 달라도 영향 범위가 어댑터에 갇힌다.
5. 합성 데이터는 «그럴듯한» 것이 아니라 **요건에서 역산한 것**을 쓴다 — 주간 주기·계절 성분·급증 이벤트·결측 구간을 의도적으로 심어 각 모듈이 그것을 잡아내는지 본다. 이 데이터셋이 §7 백테스트 하네스의 입력이 된다.

이 구조는 부수 효과가 크다. 인수 기준의 **「고정 임계치 대비 효과 비교」**(REQ-2-02)를 보고서로 쓰는 게 아니라 **재현 가능한 실행물**로 만들 수 있다.

| 태스크 | 산출 |

| 이해관계자 인터뷰 (업무 담당자·기술 담당자) | 인터뷰 기록 (SOW 14조: 협의는 서면) |
| 데이터 소스 식별 + **이력 보존 기간·품질 실측** | 데이터 요건서. **계절 학습 가능 여부 판정**(§10 R-2) |

> **G1**: 요건 정의서 검수 통과 + **정량 목표가 숫자로 적혀 있음** + 이력 데이터 보존 기간 확인. SOW 검수 절차상 10영업일이 걸리므로 5월 초에 요청해야 5월 설계가 늦지 않는다.

### Phase 3 — 모듈 개발 (6~8월, WBS 2.3)

수직 슬라이스로 간다. 「전 모듈을 반씩 만들어 8월에 잇는다」가 아니라 **한 지표에 대해 수집→임계치→알림까지 6월에 관통시키고**, 이후 모듈과 지표를 넓힌다.

| 스프린트 | 내용 | 완료 조건 |
|---|---|---|
| 6월 전반 | **관통 슬라이스 1개** — 지표 1종: Replay 수집 → 피처 → 동적 임계치 → 이상 이벤트 → Outbox → 알림 1채널 | 통합 테스트가 실제 Kafka·PostgreSQL(Testcontainers)로 관통. «Outbox 행이 생겼다»가 아니라 «수신자에게 도달했다»까지 |
| 6월 후반 | 동적 임계치 정식화 (FN-2-02) + **백테스트 하네스** | 고정 임계치 대비 오탐/미탐 수치가 자동 산출됨 |
| 7월 전반 | 예측 엔진 (FN-2-01) — Holt-Winters + 예측구간 + 사전 경고 | 백테스트에서 리드타임·적중률 산출 |
| 7월 후반 | RCA (FN-2-03) + 오케스트레이터 (FN-2-07) | 감지→분석 워크플로 라우팅 동작 |
| 8월 전반 | LLM 인사이트 엔진 (FN-2-04) — 프롬프트 DB·이력·롤백 포함 | 보고서 자동 생성. 저신뢰 결과는 «확인 필요» 표기(차단 아님) |
| 8월 후반 | 대응 추천 (FN-2-06) + 통합 계층 (FN-2-08) + MFE Admin Console | 화면에서 전 기능 확인 |

> **G3-1 (6월 말, 최우선 게이트)**: 백테스트에서 **동적 임계치가 고정 임계치 대비 정량 목표를 충족**한다. 미달이면 §4.2 탈출구(ONNX) 발동 여부를 이 시점에 결정한다 — 8월에 발견하면 되돌릴 시간이 없다.
> **G3-2 (8월 말)**: FN-2-01~04·06~08 단위 테스트 통과 + 변경 라인 커버리지 80% + ArchUnit·Modulith 검증 통과.

## 부록. 코드베이스 분석 이후 갱신된 사실

- 분석 §7.2 에서 「EWACS 저장소는 존재하지 않는다」고 적었다. 재확인 결과 `cupia/ncms/batch/tancis-batch-ewc` 가 존재하나 **Spring Batch 빈 골격**(Application 클래스 · 추상 잡 설정 · 샘플 Mapper 뿐)이며 EWACS 업무 로직은 없다. 결론은 유지되고, **`ewc` 가 TANCIS 계보의 EWACS 약어**라는 점만 추가된다 — 스키마명 `ewc_db` 의 근거가 된다.
