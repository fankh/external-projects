# 보안·권한 모델

이 문서는 포털의 접근 통제·데이터 스코핑·감사 정책을 한곳에 정리한다. 코드에 흩어진
규칙을 명시화해 화면·액션 추가 시 판단 기준으로 삼고, 보안 검토의 체크리스트로 쓴다.
개발자 온보딩은 `어댑터_연동_가이드.md`, 운영 배포는 `배포_운영_가이드.md` 를 함께 본다.

## 1. 역할 모델

계정의 역할은 4단계다 (`lib/session.ts` 의 계정 테이블, `lib/types.ts` 의 `Role`).

| 역할 | 뜻 | 통상 권한 범위 |
| --- | --- | --- |
| `USER` | 일반 임직원 | 본인 데이터(신청·서약·본인 위반·본인 계획)만 |
| `DEPT_MGR` | 부서담당(부서장) | 소속 부서 범위 (SR·서약·출력물·재택) |
| `BIZ_MGR` | 업무담당(IT·보안 운영) | 전사 운영·인프라·프로젝트·재무 리포트 |
| `ADMIN` | 시스템관리자 | 전사 + 환경설정(사용자·메뉴·코드·양식·감사) |

코드에서 자주 쓰는 파생 판정:
- `canManage = role === 'BIZ_MGR' || role === 'ADMIN'` — 전사 운영/관리 화면·집계.
- `canViewFinance = role !== 'USER'` — 재무 리포트 열람(부서담당 이상). 일반 사용자는
  본인 경영계획만. (정산 상신 주체가 부서담당이라 부서담당까지 포함 — v1.5.42)

## 2. 화면·기능(Action) 접근 통제

- **단일 원천**: 화면별 허용 역할은 `components/chrome/menus.ts` 의 `NAV` 에만 선언한다.
  내비게이션 표시, 화면 가드, 권한 매트릭스, 스모크 스위트가 모두 이 파일 하나를 따른다.
- **유효 권한(effectiveRoles)**: `lib/authz.ts` 의 `effectiveRoles(href)` 는
  `menus.ts 기본 권한 ∩ 런타임 제한(menuOverrides)` 을 돌려준다. 런타임 제한(메뉴권한
  화면, 요구사항 72행)은 **축소만** 가능해 권한 상승이 원천 차단되고, `ADMIN` 은 잠금
  방지를 위해 제한 대상에서 제외된다. 미등록 href 는 빈 배열을 돌려 **전원 차단(fail-closed)**.
- **화면 가드**: `requireMenu(href)` 는 `canAccessMenu(session, href)`(역할 유효 권한 **또는**
  사용자 그룹 위임 — 아래 '사용자 그룹 위임' 참조)이면 통과시킨다. 페이지는 역할 목록을
  중복 선언하지 않고 menus.ts 를 따른다. 미로그인 → `/login`, 권한 밖 → `/dashboard`.
- **서버 액션 가드**: `requireMenuRole(href, ...roles)` = 액션 자체의 역할 요건 ∩ 소속 화면의
  유효 권한. 서버 액션은 UI 노출과 무관하게 직접 POST 가능하므로, 화면 런타임 제한이
  **쓰기에도** 걸린다. 공용 액션(투자·비용 공유)처럼 소속 href 가 런타임 값에 따라 갈리면
  `requireRole` 로 역할만 먼저 걸고, 본문에서 `effectiveRoles(kind별 href).includes(role)` 로
  런타임 제한을 재적용한다(`finance/actions.ts` 참조).

**기능(Action) 단위 통제** (요구사항 §II '권한은 메뉴 × 기능 단위로 부여') — 화면 접근·액션
역할 요건과 별개로, 한 화면의 특정 **기능**(저장·삭제·엑셀·업로드·확정·결재)을 역할별로 더
좁힐 수 있다. 조회는 열람 자체라 항상 허용하고, 쓰기 기능만 제한한다.

- **단일 원천**: `menus.ts` 의 `SCREEN_ACTIONS: Record<href, Partial<Record<ActionKey, Role[]>>>`
  가 화면×기능 기본 권한을 선언한다(`ACTION_KEYS = save·delete·excel·upload·confirm·approve`).
  이 정의가 강제(`requireAction`)와 권한 매트릭스 표시의 **단일 원천**이라 표시와 강제가
  어긋나지 않는다(드리프트 방지). 미등록 `(href, action)` 은 기능 게이트 없음 = 화면 권한만.
- **유효 기능 권한**: `authz.ts` 의 `effectiveActionRoles(href, action)` =
  `SCREEN_ACTIONS[href][action] ∩ effectiveRoles(href) ∩ 런타임 제한(actionOverrides)`.
  화면 유효 권한과 교집합이라 기능 권한이 화면 권한을 넘어설 수 없고, `ADMIN` 은 잠금
  방지로 제외된다.
- **액션 가드**: `requireAction(href, action)` 는 `canPerformAction(session, href, action)`(역할 유효
  기능권한 **또는** 그룹 기능 위임 — §'사용자 그룹 위임' 참조)이면 통과시킨다. 서버 액션에서
  `requireMenuRole` 대신 쓰면 그 기능이 매트릭스에서 **실제로** 통제되고(표시-전용 아님, 서버 강제),
  그룹 기능 위임 대상이 된다. 현재 적용: 컴플라이언스 삭제(위험·정책·DR·점검), 인프라 삭제
  (랙·시스템·운영), 재무 확정(`confirmPlan`), SR 관리 저장(CI·SR 관리), 공지 삭제. 그룹 위임으로
  넓히고 싶지 않은 쓰기는 `requireMenuRole`(역할 전용)로 남긴다.
- **런타임 제한**: `store.actionOverrides: Record<'href#action', Role[]>` — 메뉴권한 화면의
  '기능(Action) 권한 매트릭스'(`toggleActionPerm`)에서 **축소만** 가능(권한 상승 불가).
- 한 화면의 기능 게이트는 그 화면의 모든 동종 액션을 함께 통제한다(예: `/infra/racks` delete =
  랙·H/W 삭제 공통). 새 파괴적/통제 기능은 `SCREEN_ACTIONS` 등록 + `requireAction` 가드로
  추가하면 매트릭스에 자동 노출·서버 강제된다(§6 규칙 참조).

**사용자 그룹 위임** (구성 가능한 가법 계층 — `/settings/groups`) — 4 고정 역할 위에 얹어 특정 사용자에게
운영 화면의 **열람**과 관리자가 명시한 **특정 쓰기 기능**을 위임한다. 재사용 프레임워크의 고객별
커스터마이즈를 역할 재설계 없이 충족하는 계층이다. **옵트인**(부여 없으면 동작 불변)이라 엄격 역할 기반
쓰기를 원하는 조직은 이 계층을 쓰지 않으면 된다(강제 변경 아님).

- **모델**: `store.userGroups: UserGroup[]`(`{ id, label, description?, members, menuGrants, actionGrants?, expiresAt? }`).
  관리자가 그룹에 **구성원**(`Session.name`)·**부여 메뉴**(NAV href, 열람)·**부여 기능**(`${href}#${action}`,
  쓰기)을 지정한다. 세션 쿠키가 아니라 스토어에서 **실시간 해석**하므로 그룹 변경이 재로그인 없이 즉시 반영된다.
- **단일 술어(열람)**: `canAccessMenu(session, href)` = `effectiveRoles(href).includes(role)` **OR**
  `groupGrantsMenu(name, href)`. 내비 표시(`layout` 의 `grantedHrefs`)와 서버 가드(`requireMenu`)가 이 술어
  하나를 공유해 **표시=강제** 정합을 유지한다. 액션 위임을 받은 화면도 열람이 함께 열린다(기능을 쓰려면 진입 필요).
- **단일 술어(기능)**: `canPerformAction(session, href, action)` = `effectiveActionRoles(href, action).includes(role)`
  **OR** `groupGrantsAction(name, href, action)`. `requireAction`(강제)과 화면 쓰기 컨트롤 표시가 이 술어를 공유한다.
- **경계 — 위임 가능 대상만**: 열람 위임은 `isGrantableMenu`(비관리자 역할이 있는 운영 화면), 기능 위임은
  `isGrantableAction`(**SCREEN_ACTIONS 등록 액션** && `isGrantableMenu`)만 인정한다. ADMIN 전용 화면·미등록
  액션·관리 기능은 위임 불가. 읽기 시점에 필터하므로 손상·위조 데이터(수기 편집 `PORTAL_DATA_FILE`)가
  admin 화면/미등록 액션을 위임해도 무시된다(fail-closed). UI 목록·`toggleGrant`/`toggleActionGrant`·해석 **3중** 차단.
- **`requireMenuRole` 은 역할 전용 유지**: 기능 위임은 `requireAction` 카탈로그(SCREEN_ACTIONS)만 넓힌다.
  `requireMenuRole` 로 가드한 쓰기(계약 등록·재평가·효율화 등)는 위임으로 뚫리지 않는다 — 부여하지 않은
  쓰기는 그대로 역할이 막는다. ADMIN 화면 쓰기(예: 메뉴권한 토글 = `requireMenu`)도 위임 대상이 아니므로 안전.
- **컨트롤 표시 정합**: 역할로 쓰기 컨트롤을 숨기는 화면(compliance 삭제·finance 확정)은 표시 조건을
  `canManage || groupGrantsAction(...)` 로 확장해 위임받은 사용자에게 컨트롤을 노출한다(그 외 관리 컨트롤은
  `canManage` 유지). `canPerformAction`(런타임 제한 반영) 대신 `canManage||groupGrantsAction`(위임분만 가산)을
  쓰는 이유: 기존 역할 표시 동작을 보존해 기능 권한 매트릭스(actionOverrides) 테스트에 회귀를 내지 않기 위함.
  항상-렌더 화면(infra·sr·inspection)은 서버 강제만으로 이미 동작. 서버 액션의 추가 가드(예: board/notices 의
  소유자 체크)로 위임이 무효인 화면은 표시 확장 대상이 아니다.
- **만료·자동 회수(임시 위임)**: 그룹에 `expiresAt`(YYYY-MM-DD, 선택)을 두면 만료일이 지난 그룹은 열람·기능
  위임을 일절 부여하지 않는다 — `isGroupActive(grp)` 를 4 리졸버가 모두 가드하므로 재로그인·배치 없이 **읽기
  시점에 자동 회수**된다(미지정=무기한). 만료 판정은 `!expiresAt || today() <= expiresAt` 이되, 사전식 문자열
  비교가 형식오염 날짜(비-영벌충 `2026-2-5`·달력부재 `2026-13-01`)를 '미만료'로 오판하는 fail-open 을 막기 위해
  **실 달력 유효성(`isCalendarDate`)을 먼저 본다 — 유효한 달력 날짜가 아니면 만료로 취급(fail-closed)**.
  입력(만료일 설정)도 같은 검증으로 달력 부재 날짜를 거부한다. 같은 규약이 공통코드 사용기간(`isCodeActive`)에도
  적용된다(만료 코드는 신규 선택지에서 제외).
- **위임 현황 대장·증적**: `groupDelegationRegister()` 가 현재 유효한(만료 제외) 그룹의 위임을 구성원 단위로 펼친
  접근검토 대장(구성원·유형(열람/기능)·부여 대상·소속 그룹·만료)을 낸다. `/settings/groups` 화면과 엑셀
  export(`type=group-delegations`, ADMIN 전용 게이트)가 이 **단일 원천**을 공유해 화면=export 드리프트가 없다.
  ISMS 접근검토(누가 무엇을 위임받았나)의 오프라인 증적.
- **감사**: 그룹 생성·삭제·구성원·부여(메뉴·기능)·만료일 토글은 모두 `'사용자 그룹 변경'` 으로 남는다(§5).

## 3. 데이터 스코핑

화면에 진입할 권한이 있어도, 목록·집계는 역할별로 다시 좁힌다. 검색(`/search`)도 각
도메인의 스코핑을 그대로 따라 우회 경로가 되지 않는다.

| 화면 | USER | DEPT_MGR | BIZ_MGR · ADMIN |
| --- | --- | --- | --- |
| SR 신청내역 | 본인 신청 | 소속 부서 | 전사 |
| 경영계획(투자·비용) | 본인 작성 | 소속 부서 | 전사 |
| 재무 리포트(계약·정산·속보·계획대비실적) | **차단** | 전사 | 전사 |
| 보안서약 현황 | 본인 | 소속 부서 | 전사 |
| 출력물 폐기현황 | 본인 | 소속 부서 | 전사 |
| 재택 체크리스트 | 본인(대상 시) | 소속 부서 | 전사 |
| 보안위반 | 본인 건 | 본인 건 | 전사(등록·조회) |
| 보안교육 | 본인 이수 + 전사 이수율 | 본인 이수 + 전사 이수율 | 전 임직원 이수현황 |
| 개인별현황(대시보드) | 본인 항목 | 본인 항목 | 본인 + 전사 운영 스냅샷 |
| 인프라·프로젝트·CI SR | 접근 불가 | 접근 불가 | 전사 |
| 게시판(공지·QnA) | 전체 열람 | 전체 열람 | 전체 열람 |

전사 이수율 같은 **비개인 집계 수치**는 전 역할에 노출해도 개인정보 누출이 아니므로 허용한다.
개인 명단·타인 상세는 `canManage` 로 가린다.

## 4. 엑셀 다운로드(export)

`/api/export?type=…` 는 화면과 **동일한 권한·스코핑을 서버에서 재적용**한다
(`app/api/export/route.ts`). 두 겹으로 막는다:
1. `effectiveRoles(소속 화면 href).includes(role)` — 런타임 메뉴 제한이 다운로드에도 걸린다.
2. 유형별 추가 가드 — 재무 리포트(`invest-actual`·`expense-actual`·`expense-flash`)는
   USER 403, 부서 스코핑 유형(SR·서약·출력물·재택)은 `role`·`dept` 로 행을 좁힌다.

화면의 다운로드 버튼과 라우트 처리 유형은 1:1 로 일치해야 한다(현재 35종, 위임 현황 `group-delegations` 포함).

## 5. 감사(audit) 정책

감사 이력(`/settings/audit`, `lib/audit.ts`)은 **선택적**이다 — 모든 변경이 아니라
아래 원칙에 해당하는 행위만 남긴다. 행위 종류는 `AuditAction` 통제 어휘로 고정한다.

**감사 대상** — 설정·정책·명단을 바꾸거나, 특정인의 의무·신분에 영향을 주거나, 데이터를
파기하거나, 결재 워크플로를 진행하는 행위:
- 결재 상신·승인·반려·회수, 결재선 변경
- 공통코드·메뉴권한·사용자 그룹·엑셀양식·서약양식·점검 기준·연동 채널·인프라 자산 변경
- 재택 대상자(명단) 변경
- 게시물 삭제 등 레코드 삭제
- **등록 provenance** — 레코드에 작성자·등록자 필드가 없어 '누가 등록했나'가 감사로만
  추적되는 등록. 보안위반 등록(타인 지목, v1.5.44)·장애 등록·재무 속보 등록(v1.5.385)·
  인프라 변경 등록(v1.5.387)·점검계획 등록(v1.5.389)이 여기 해당한다. 형제 액션(수정·삭제·
  동종 형제화면 등록)은 감사에 남는데 등록만 무기록이면 provenance 사슬이 끊긴다.
- 배치 실행·이관, 인사정보 동기화

**감사 비대상** — 도메인 레코드나 후속 결재가 추적을 대신하는 행위:
- 개인 submission: 보안서약 서명, 재택 체크리스트 제출, 출력물 폐기 등록 — 도메인 현황
  화면이 곧 추적 지점(누가·언제·방식이 레코드에 남는다).
- 작성자 필드를 가진 등록: 경영계획(`owner`)·보안성 검토(`reviewer`=본인)·CI SR
  (`receivedBy`) 등록 — 레코드 자체가 등록자 provenance 라 별도 감사 불필요.
- 후속 결재가 추적하는 진행: SR/적용요청·정산품의·점검결과 상신 등 — `draftApproval` 이
  '결재 상신' 감사로 기안자를 남긴다.

**경계 판단**: 설정/정책 변경, 특정인의 의무·신분 영향, 데이터 파기, 결재 진행은 감사한다.
운영 레코드 등록은 **레코드에 작성자·등록자 필드가 있거나 후속 결재가 추적하면 비대상**,
그런 provenance 가 없어 감사가 유일한 추적점이면 대상이다(위 '등록 provenance' 규칙). 운영
CRUD 를 무조건 감사하지도, 무조건 생략하지도 않는다 — provenance 유무로 가른다.

## 6. 서버 액션 작성 규칙

새 서버 액션·화면을 추가할 때 지킨다(적대 리뷰에서 반복 확인된 규칙):
1. `requireMenuRole('<소속 href>', ...역할)` 로 가드한다 — `requireRole` 단독은 런타임 메뉴
   제한을 우회하므로 금지(공용 액션 예외는 §2 참조). 파괴적·통제 기능(삭제·확정 등)을 기능
   매트릭스에서 통제하려면 `SCREEN_ACTIONS` 등록 + `requireAction(href, action)` 로 가드한다
   (§2 '기능(Action) 단위 통제').
2. 공유 컬렉션(예: `investPlans` 는 투자·비용 공유)을 만지는 액션은 `kind`/소속 필터를
   반드시 재검증한다 — 안 그러면 옆 화면의 제한을 우회한다.
3. 숫자 입력은 `Number.isFinite` + 범위 상한(금액 1e9 등), 문자열은 길이 상한·필수 검증.
4. 엑셀 유형을 추가하면 `EXPORT_MENU` 에 소속 화면을 등록한다.
5. §5 의 감사 대상에 해당하면 `audit(행위자, AuditAction, 상세)` 를 남긴다. 레코드 등록
   액션은 §5 '등록 provenance' 규칙으로 판단(작성자 필드가 없고 형제가 감사되면 등록도 남김).
   필요 시 `AuditAction` 어휘를 확장하되, `settings/audit` 의 `ACTION_TONE` 은 strict
   `Record<AuditAction>` 라 새 액션의 톤 매핑을 함께 넣지 않으면 **빌드 오류**가 난다.
6. 목록·집계를 렌더하면 §3 스코핑을 적용한다 — 검색(`/search`)에도 같은 스코핑을 반영한다.
7. `nextNo(...)` 로 채번한 뒤 스토어 커밋(`push`/`unshift`)까지 사이에 `await` 를 두지
   않는다 — 인메모리 스토어는 단일 스레드지만 `await` 지점에서 다른 요청이 끼어들어 같은
   번호를 채번할 수 있다. 채번→커밋은 동기 임계구역으로 유지하고, 어댑터·메일 등 `await` 는
   커밋 뒤에 둔다(또는 가드처럼 채번 앞에). 외부 시스템이 번호를 부여하는 값(예: 자산등록번호
   `acquireAssetNo`)은 어댑터가 유일성을 책임지므로 이 규칙과 무관하다.
8. `requireMenu(href)` 는 **열람 술어**(`canAccessMenu` — 역할 OR 그룹 위임)라 그룹 위임받은
   비관리자도 통과한다. 따라서 **쓰기 액션 가드로 `requireMenu` 를 쓰지 않는다** — 반드시
   `requireMenuRole` 또는 `requireAction` 을 쓴다. 이 둘의 성격은 다르다: `requireMenuRole` 은
   **역할 전용**(그룹 위임이 통과할 수 없음)이고, `requireAction` 은 SCREEN_ACTIONS 등록 액션에
   대해 **역할 OR 그룹 기능 위임**(`canPerformAction`)을 통과시킨다. 그러므로 그룹 기능 위임으로
   넓히고 싶지 않은 쓰기(관리성·비카탈로그)는 `requireMenuRole` 로, 매트릭스·위임 대상으로 삼을
   쓰기는 `SCREEN_ACTIONS` 등록 + `requireAction` 으로 가드한다. ADMIN 전용 화면은 그룹 위임 대상이
   아니므로(`isGrantableMenu`=false) 그 화면의 `requireMenu` 는 사실상 ADMIN 게이트로 남지만, 새
   화면을 만들 때 이 등가에 의존하지 말고 액션은 명시적 가드를 붙인다. authz 술어를 넓히는 변경
   (그룹·위임 등)을 할 때는 `requireMenu` 를 액션 가드로 쓰던 기존 화면을 전수 감사한다
   (`'use server'` + `requireMenu` grep). 역할로 컨트롤을 숨기는 화면을 위임 표시로 확장할 때는
   `canManage || groupGrantsAction(...)` 을 쓰고(기존 역할 표시 보존), 서버 액션의 추가 가드
   (소유자 체크 등)로 위임이 무효인 화면은 표시를 확장하지 않는다.
