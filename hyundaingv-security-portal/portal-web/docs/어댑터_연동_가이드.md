# 연동 어댑터 개발 가이드

새 고객사의 실제 시스템(그룹웨어·인사·자산·보안)을 포털에 붙이는 절차를 다룬다. 포털 본체는
`lib/integrations/types.ts`의 어댑터 계약만 알고, 고객사별 구현은 어댑터로 캡슐화한다. 데모의
목업 어댑터(`lib/integrations/mock.ts`)를 고객사 구현으로 교체하는 것이 커스터마이징의 전부이며,
포털 화면·서버 로직은 손대지 않는다.

전제: 코드 구조·게이트는 [`docs/구축_요약.md`](구축_요약.md), 미구현 항목·착수 기준은
[`docs/로드맵.md`](로드맵.md)를 함께 본다.

---

## 1. 어댑터 계약

계약의 단일 원천은 `lib/integrations/types.ts`다. 아래는 요약이며, 시그니처가 바뀌면 항상
`types.ts`가 우선한다.

| 종류 | 인터페이스 | 메서드 | 대체 대상 시스템 |
|------|-----------|--------|-----------------|
| 메시징 | `MessagingAdapter` | `send(to, subject): Promise<SendResult>` | 그룹웨어 메일 · 홈페이지 서버 SMS |
| 인사 | `HrAdapter` | `fetchPeople(): Promise<Person[]>` | 인사·근태 시스템(일배치) |
| 자산 | `AssetAdapter` | `searchAssets(query)` · `acquireAssetNo(serial)` | 자산관리시스템 REST API |
| 보안자료 | `SecdataAdapter` | `fetchPrintouts(): Promise<PrintoutSourceRow[]>` | 보안·출력물 시스템 DB 연계 |

결재(`approval`)·SSO(`sso`) 채널은 아직 계약이 열려 있다(로드맵 1·2). 프로필에서 `planned: true`로
바인딩하면 화면에 '연동 예정'으로 표시되고 활성 집계·자가진단에서 제외된다.

`Person`은 `{ name, dept }`, `SendResult`는 `{ ok, detail }`, `ExternalAsset`·`PrintoutSourceRow`의
필드는 `types.ts`에 정의돼 있다.

---

## 2. 오류·타임아웃 계약 (중요)

어댑터 구현은 실패 처리를 스스로 떠안지 않는다. 포털이 호출 경계에서 흡수한다.

- **예외(throw)는 그대로 던져도 된다.** 네트워크 오류·인증 실패·비정상 응답이면 `throw`하라.
  포털의 모든 어댑터 호출부는 이를 실패 이력(발송 로그·배치 실패)으로 기록하고 화면·스케줄러가
  죽지 않게 흡수한다. 예외 메시지는 실패 상세로 남으므로 원인을 담아 던지는 편이 좋다.
- **자체 타임아웃을 넣지 마라.** 포털이 모든 어댑터 호출을 `withTimeout`(기본 10초,
  `PORTAL_ADAPTER_TIMEOUT_MS`로 조정)으로 감싼다. 응답이 없으면 포털이 상한 시간에 끊어
  실패로 처리한다. 어댑터에 경쟁하는 타임아웃을 두면 값만 이원화된다.
- **소프트 실패는 `SendResult.ok = false`로.** 메시징은 예외 대신 `{ ok: false, detail }`로
  '보냈지만 일부 실패' 같은 상태를 표현할 수 있다. 이 경우도 발송 로그에 남는다.

즉 어댑터 작성자는 정상 경로와 '실패 시 throw'만 신경 쓰면 된다. 재시도·타임아웃·이력 적재는
프레임워크 몫이다.

## 3. 온보딩 4단계

### 3-1. 어댑터 구현

`lib/integrations/`에 고객사 파일을 만들고 계약을 구현한다. **복사해서 시작할 컴파일 검증된
참조 구현이 [`lib/integrations/examples/rest-adapters.example.ts`](../lib/integrations/examples/rest-adapters.example.ts)에
있다** — REST 기반 인사·메일·자산 어댑터 전체 예시로, registry 에 등록되지 않아 런타임엔
영향이 없지만 빌드에서 타입 검증을 받아 인터페이스가 바뀌면 같이 오류가 나므로 낡지 않는다.
이 파일을 `lib/integrations/<고객사>.ts` 로 복사한 뒤 엔드포인트·인증·스키마 매핑만 고친다.

**실동작 메시징·HR 어댑터**는 [`lib/integrations/rest.ts`](../lib/integrations/rest.ts)에 이미 구현돼
있다(`restMail`·`restSms`·`restHr`) — 예시가 아니라 registry 에 등록된 실 어댑터로, 샘플 고객사 프로필
(제조·공공·금융)의 메일·문자·인사가 여기에 바인딩된다.
- **메시징**: 엔드포인트·인증·발신자를 환경변수(`PORTAL_MAIL_API_URL`·`PORTAL_MAIL_API_TOKEN`·
  `PORTAL_MAIL_FROM`, 문자는 `PORTAL_SMS_*`)로 주입. 발송 페이로드 `{to, subject, from}` JSON.
- **HR 디렉터리**: `PORTAL_HR_API_URL`(·`PORTAL_HR_API_TOKEN`)로 실 HR API GET, 응답을
  `Person{name,dept}` 으로 매핑. 고객 스키마 필드명이 다르면 `PORTAL_HR_NAME_FIELD`·`PORTAL_HR_DEPT_FIELD`
  로 지정. 미설정 시 부트스트랩 명단을 반환(자가진단 통과), 설정 시 실 응답으로 대체.
- **자산**: `PORTAL_ASSET_API_URL` GET(`?q=`)로 자산 조회, `PORTAL_ASSET_REGISTER_URL` POST(`{serial}` →
  `{assetNo}`)로 신규 자산등록번호 취득(쓰기 폐쇄루프). 인증 `PORTAL_ASSET_API_TOKEN`. 조회 미설정 시 빈
  배열(자가진단 통과), 취득 미설정 시 예외(액션이 흡수).
- **보안관제**: `PORTAL_SECMON_API_URL` GET 으로 탐지 이벤트 조회, `SecurityEvent` 로 매핑하고 탐지 유형을
  포털 위반 유형 3종으로 정규화(→ `lib/secmon.ts` 가 보안위반 자동 편입). 인증 `PORTAL_SECMON_API_TOKEN`.
  미설정 시 빈 배열. sec-monitor 채널은 기본 off — 실 배포에서 채널 ON 필요.
- **출력물**: `PORTAL_SECDATA_API_URL` GET 으로 전일자 출력물 자료 조회, `PrintoutSourceRow` 로 매핑(매수는
  수치·개인정보 포함은 불리언 강제 변환). 인증 `PORTAL_SECDATA_API_TOKEN`. 미설정 시 빈 배열. security-db
  채널은 기본 off.

- **전자결재**: `PORTAL_APPROVAL_API_URL` POST(`ApprovalPushDoc`→`{externalId}`)로 포털 대기 결재를 외부
  그룹웨어 결재함에 푸시(연동 id 취득). 인증 `PORTAL_APPROVAL_API_TOKEN`. 자가진단 프로브(docId `__probe`)는
  네트워크 없이 합성 id 반환 — 실 그룹웨어에 유령 결재를 만들지 않는다. 상신 시점과 분리된 배치 푸시라 외부
  장애가 포털 상신을 막지 않는다.

- **SSO(SAML)**: `SsoAdapter`(`lib/integrations/saml.ts` `samlSso`) — loginRedirect(SP-initiated AuthnRequest,
  HTTP-Redirect 바인딩)·verifyResponse(RSA-SHA256 어설션 서명 검증 + 조건). IdP·SP 메타데이터는 환경변수
  (`PORTAL_SAML_IDP_SSO_URL`·`PORTAL_SAML_IDP_CERT`\[`_FILE`\]·`PORTAL_SAML_SP_ENTITY_ID`·`PORTAL_SAML_SP_ACS_URL`).
  로그인 라우트 `/api/sso/login`(시작)·`/api/sso/acs`(어설션 수용)·`/api/sso/metadata`(SP 메타데이터 —
  IdP 신뢰 구성용). 참조는 어설션 직렬 바이트에 서명 검증하고, 실 배포는 XML-DSig(C14N) 라이브러리로 교체(계약 동일).

계약 8종(메일·문자·전자결재·SSO·인사·자산·보안관제·출력물) 전부 실 구현이 있다 — 게이트웨이·IdP·스키마가
다르면 이 파일(또는 saml.ts)의 매핑·검증만 조정하면 된다. planned 채널 없음.

핵심은 고객 스키마를 포털 계약으로 매핑하는 것이다(예: 인사 응답 → `Person{name,dept}`):

```ts
export const acmeHr: HrAdapter = {
  async fetchPeople(): Promise<Person[]> {
    // 타임아웃은 포털 withTimeout 이 담당 — 여기서 걸지 않는다.
    const res = await fetch(`${BASE}/api/v1/employees`, { headers: auth() })
    if (!res.ok) throw new Error(`ACME 인사 API ${res.status}`) // 포털이 실패로 흡수
    const rows = (await res.json()) as Array<{ empName: string; orgName: string }>
    return rows.map((r) => ({ name: r.empName, dept: r.orgName })) // 고객 스키마 → Person
  },
}
```

DB 연계·SAML 방식도 같은 계약을 만족하면 된다. 구현체는 목업(`mock.ts`)과 동일한 형태의
객체 리터럴이다.

### 3-2. registry 등록

`lib/integrations/registry.ts`의 종류별 맵(`MESSAGING`·`HR`·`ASSET`·`SECDATA`)에 `adapterId → 구현`을
추가한다. `adapterId`는 다음 단계의 채널 바인딩에서 참조하는 문자열 키다.

```ts
import { acmeHr, acmeMail } from './acme'

const MESSAGING: Record<string, MessagingAdapter> = { /* ... */ 'acme-mail': acmeMail }
const HR: Record<string, HrAdapter> = { /* ... */ 'acme-hr': acmeHr }
```

### 3-3. 고객사 프로필 작성·등록

`profiles/acme.config.ts`에 브랜딩과 채널 바인딩을 둔다. 채널이 3-2의 `adapterId`를 가리킨다.
`profiles/sample-manufacturer.config.ts`를 참고 템플릿으로 복사해 고치는 것이 빠르다.

```ts
// profiles/acme.config.ts
import type { ChannelBinding, PortalBrand } from '@/lib/integrations/types'

export const PORTAL: PortalBrand = {
  customer: '(주)에이스', productName: 'ACME IT PORTAL',
  productSub: 'IT · Security Governance', version: 'v1.0',
}

export const CHANNELS: ChannelBinding[] = [
  { id: 'groupware-mail', kind: 'mail', name: '그룹웨어 메일', transport: 'REST API',
    usage: '안내메일 발송', adapterId: 'acme-mail', enabledByDefault: true },
  { id: 'hr-sync', kind: 'hr', name: '인사 시스템', transport: 'REST API',
    usage: '사용자 기본정보 동기화', adapterId: 'acme-hr', enabledByDefault: true },
  // 자산·보안자료·결재·SSO 채널은 계약 범위에 맞춰 추가하거나 planned: true 로 표시
]
```

그리고 `profiles/registry.ts`의 `ALL_PROFILES`에 한 줄 올린다. 이 파일이 전 프로필의 단일
원천이라, 런타임 선택(`portal.config.ts`)과 계약 자가진단(`conformance.ts`)이 함께 이 프로필을
집어 간다 — 두 곳에 따로 등록하다 한쪽을 빠뜨리는 실수가 없다.

```ts
// profiles/registry.ts
import * as acmeProfile from './acme.config'
export const ALL_PROFILES: Record<string, typeof defaultProfile> = {
  default: defaultProfile, manufacturer: manufacturerProfile, public: publicProfile, acme: acmeProfile,
}
```

이제 `PORTAL_PROFILE=acme`로 실행하면 이 고객사 구성이 그대로 뜬다. 한 번 빌드한 이미지가
환경변수만으로 고객사를 전환한다 — 프로필별 재빌드가 없다.

### 3-4. 자가진단·게이트로 검증

연동·인프라 화면의 **어댑터 계약 자가진단** 카드가 전 채널의 바인딩 완결성(`adapterId`가
registry에서 해석되는가)과 계약 적합성(어댑터를 실제 호출해 반환형이 맞는가)을 부작용 없이
검사한다. 위반이 있으면 즉시 카드에 드러난다.

단, 자가진단은 **목업 어댑터도 유효 어댑터로 통과**한다(계약을 만족하므로) — '위반 0'이 곧
'실 시스템 연결'을 뜻하지 않는다. 실 연결 여부는 같은 화면의 **배포 준비 상태** 카드로 확인한다:
`연동 어댑터`(활성 채널의 실/목업 집계 — 전량 목업이면 오프라인 데모 상태) · `SSO(SAML)`
(SSO 사용 시 구성됨 여부). 프로덕션 기동 로그의 `배포 준비 경고`가 배포 직후 오구성(전량 목업·
비영속·HTTP 쿠키)을 로그에서 즉시 알린다 — 로그인 없이도 CI·로그 모니터링이 잡는다.

```bash
PORTAL_PROFILE=acme npm run gates   # 빌드·스모크·접근성·견고성·세션·헬스·e2e 전량
```

프로필 전환 e2e(`profile`·`profile_public` 시나리오)가 고객사 스위칭을 검증하므로, 새 프로필도
동일 패턴으로 스모크에 needle을 추가하면 회귀 방지선이 된다.

## 4. 배포 환경변수

| 변수 | 용도 | 기본값 |
|------|------|--------|
| `SESSION_SECRET` | 세션 쿠키 HMAC 서명 키 (**필수**, 미설정 시 개발키로 위조 가능) | 개발키(경고) |
| `PORTAL_PROFILE` | 고객사 프로필 선택 | `default` |
| `PORTAL_DATA_FILE` | 파일 기반 영속화 경로 (미설정 시 인메모리) | 없음 |
| `PORTAL_COOKIE_SECURE` | HTTPS 배포 시 `1` — 쿠키 Secure 속성 | 없음 |
| `PORTAL_NOTIFY_INTERVAL_MS` | 알림 배치 주기(ms) — 설정 시 스케줄러 기동 | 없음(수동) |
| `PORTAL_ADAPTER_TIMEOUT_MS` | 어댑터 호출 상한 시간 | `10000` |

전체 참조는 [`.env.example`](../.env.example)에 있다.

## 5. 온보딩 체크리스트

- [ ] 계약 5종 중 고객사 범위에 해당하는 어댑터를 `lib/integrations/`에 구현 (실패 시 throw, 자체 타임아웃 없음)
- [ ] `registry.ts` 종류별 맵에 `adapterId → 구현` 등록
- [ ] `profiles/<고객사>.config.ts`에 브랜딩·채널 바인딩 작성, `profiles/registry.ts` `ALL_PROFILES`에 등록
- [ ] 범위 밖 채널은 `planned: true` 또는 `enabledByDefault: false`로 표시
- [ ] `SESSION_SECRET` 등 배포 환경변수 주입, HTTPS면 `PORTAL_COOKIE_SECURE=1`
- [ ] `PORTAL_PROFILE=<고객사> npm run gates` 그린, 자가진단 카드 위반 0
- [ ] **배포 준비 상태** 카드 확인 — `연동 어댑터`가 '실'(전량 목업이면 실 어댑터로 교체), SSO
  사용 시 `SSO(SAML)` 구성됨, 프로덕션 기동 로그에 `배포 준비 경고` 잔여 없음 (자가진단 위반 0
  ≠ 실 연결 완료)
