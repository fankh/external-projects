# 릴리스 노트 — portal-web v1.5.181

이 릴리스는 SR 상태 기계의 **영구 고착 결함**을 고친다. 시스템개발 SR 이 적용요청 상태에서 변경관리에 편입된
뒤 중지되면, 변경결과 승인이 SR 을 완료로 전파하지 못해 SR 이 적용요청에 영원히 갇히는 결함이 있었다. 이를
막고, 겸사겸사 5곳에 흩어져 있던 지연 SR 판정을 한 곳으로 모았다. 전 게이트가 그린이다.

## 주요 변경

### SR 중지-변경 고착 결함 수정 (핵심)
**증상.** 시스템개발 SR 은 수동 완료 경로가 없고, 변경관리 최종완료가 매칭 SR 을 완료로 전파한다
(`work/approvals/actions.ts`, `sr.status === '적용요청'` 조건). 그런데 변경 결재는 `cw.id` 로 키잉되므로,
`suspendSr` 의 기존 가드(`approvals.some(a => a.ref === srNo && a.status === '대기')`)에 걸리지 않아 변경
진행 중에도 SR 을 중지할 수 있었다. 중지(`status='중지'`) 상태에서 변경결과가 승인되면 전파 조건
(`=== '적용요청'`)이 거짓이라 SR 이 완료되지 않고, 변경만 최종완료가 된다. 재개하면 SR 은 적용요청으로
돌아오지만 이미 최종완료된 변경은 재편입도 안 되고(변경관리 `matchable`·`addDevChange` 가 기존 변경 존재 시
차단) 수동 완료 경로도 없어 **영구 고착**된다.

**수정.**
- **1차 가드** — `suspendSr` 에서 비-최종완료 변경에 편입된 SR 의 중지를 금지(`s.changes.some(c => c.srNo === srNo && c.status !== '최종완료')`). 변경 미편입 적용요청 SR 은 정상적으로 중지 가능.
- **2차(방어)** — `resumeSr` 에서 복원 상태가 적용요청인데 매칭 변경이 이미 최종완료면 완료로 닫아, 가드 이전
  데이터의 고아 상태도 해소한다.

### SR 지연 판정 단일 원천 (동반)
지연 SR 판정(`완료예정일 경과 + 활성 상태`)이 화면(sr/delayed 읽기·재계획 가드)·대시보드·IT운영 종합
export·알림 배치 5곳에 리터럴로 복제돼 있었다. 새 `lib/sr.ts` `isSrDelayed`/`delayedSrs`/`isSrReplannable`
(+`SR_INACTIVE_STATUSES`)로 통합해, 활성 제외 상태 집합이 바뀌어도 한 곳만 고치면 모든 소비처가 정합을 유지한다.

## 호환성·영향
- 무회귀: 지연 판정 리팩터는 동일 술어를 헬퍼로 옮긴 것(수치·동작 불변). 저장 스키마 변경 없음.
- 결함 수정은 정상 흐름(변경 미편입 SR 중지·재개, 변경 정상 최종완료 전파)을 바꾸지 않는다.
