# 로드맵 — v1.0 이후

v1.0(태그 `portal-web-v1.0`)은 데모·제안 범위의 봉인 지점이다. 요구사항 3개 시트가
소진됐고 게이트 3종이 녹색이므로, 이후 작업은 아래 실고객 접점에서만 시작한다.
각 항목은 착수 조건(외부 입력)과 완료 기준을 함께 적는다.

## 1. 고객사 어댑터 실구현

- **착수 조건**: 고객사 시스템 접속 정보·API 명세(그룹웨어 메일/결재, 인사·근태,
  자산관리, 보안·출력물 DB) 접수.
- **작업**: `lib/integrations/` 에 어댑터 구현 추가, `profiles/<고객사>.config.ts` 작성,
  `portal.config.ts` 선택지 등록. 포털 본체는 무변경이 원칙 — 본체 수정이 필요해지면
  어댑터 계약(`lib/integrations/types.ts`)의 결함이므로 계약을 먼저 고친다.
- **완료 기준**: e2e `profile` 시나리오와 동형의 고객사 시나리오 추가 통과 +
  스테이징에서 실 시스템 대상 왕복 1회(메일 수신, 자산번호 취득 등) 확인.

## 2. SAML SSO 연동

- **착수 조건**: 고객사 IdP 메타데이터(엔드포인트·인증서) 접수.
- **작업**: 로그인 화면의 목업 계정 선택을 SAML 어설션 처리로 교체. 세션 발급은
  기존 `signSession()` 을 그대로 쓰고, 어설션의 사번·권한그룹을 `Session` 으로 매핑한다.
  목업 로그인은 `PORTAL_PROFILE` 과 같은 방식의 환경 스위치로 개발용으로 보존한다.
- **완료 기준**: IdP 로그인 → 권한그룹별 메뉴 노출 확인 + 스모크의 세션 부정 검증
  (변조·만료) 4건이 SAML 세션에서도 통과.

## 3. MS-SQL 전환

- **착수 조건**: 운영 DB 인프라 확정.
- **작업**: `lib/store.ts` 의 컬렉션을 테이블로 이관(요구사항의 테이블 힌트:
  service_requests·failures·modifications·company_pledges·printout_discards·violations·
  excel_templates·pages·boards). 뮤테이션이 전부 서버 액션의 `getStore()` 경유이므로
  저장 계층 교체 지점이 한 곳이다. 개인정보 컬럼 암호화(제품안내서 §VI) 포함.
- **완료 기준**: 게이트 3종을 DB 백엔드로 전부 통과 + 동시 사용자 부하 기본 검증.

## 4. 데모 피드백 반영

- **착수 조건**: 시연(docs/데모_시나리오.md) 후 고객 피드백 접수.
- **작업**: 피드백을 요구사항 시트 형식으로 정리해 우선순위 합의 후, 기존 사이클
  방식(폐쇄 루프 단위 + 게이트 + 커밋)으로 반영.

## 운영 수칙

- 어떤 변경이든 커밋 전 `npm run smoke && npm run health && npm run e2e` 를 돌린다.
- 새 화면·권한은 `components/chrome/menus.ts` 한 곳에서 시작한다(내비·가드·매트릭스·
  스모크가 따라온다). 새 결재 유형은 `ApprovalDocType` 추가 → `draftApproval` 상신 →
  `work/approvals/actions.ts` 전파 순서다.
- 병렬 세션과 같은 저장소를 쓸 때 테스트 포트는 3500번대(이 프로젝트) 를 유지한다.
