# 릴리스 노트 — portal-web v1.5.245

정산품의 삭제(v1.5.239)가 폐기된 품의의 첨부(정산 증빙)·결재 기록을 남겨, id 재사용 시 신규 정산에
유령 첨부·이전 회차 결재로 새어 나오던 결함을 고쳤다. deleteSettlement 이 품의만 제거하고 s.attachments·
s.approvals 의 참조를 지우지 않아, 최상위 id 품의를 삭제하면 nextNo(최대 id+1)가 그 id 를 재사용하고, 같은
id 로 만든 새 정산의 결재함 상세에 삭제된 품의의 증빙 파일과 '이전 회차' 반려 결재가 표시됐다.

## 배경 — 발견 경위

고아-할일 클래스 정리(v1.5.241·243) 후, 병렬 클래스인 '삭제 시 참조 자취 잔존'을 점검하다 발견.
deleteQna·deleteNotice 는 삭제 시 s.attachments 를 함께 정리하는데(같은 id 재사용 시 유령 첨부 방지),
deleteSettlement(v1.5.239 신규)만 이 정리를 빠뜨렸다. 정산은 증빙 첨부(registerUpload)와 결재(draftApproval)를
모두 가지므로, 첨부·결재 양쪽 자취가 남아 id 재사용 시 결재함 상세(work/approvals: attachCount(ref)·refId 매칭
파일 목록·같은 ref 이전 회차)로 새어 나온다.

## 주요 변경
- `app/(app)/finance/actions.ts` `deleteSettlement`: 품의 제거 후 `s.attachments`(refId===id)와 `s.approvals`
  (ref===id)의 자취를 함께 정리. deleteQna·deleteNotice 의 첨부 정리와 동일 정책. §VI 추적은 감사 로그
  ('정산품의 삭제')가 담당하므로 결재함 자취 제거는 무해. 대기 결재는 기존 가드로 이미 삭제 대상에서 배제.

## 호환성·영향
- 무회귀: 삭제 자체·상태/소유자/메뉴 가드·감사·재상신 할일 폐쇄(v1.5.241) 무변경. 첨부·결재 자취만 추가 정리.
- 정상 반려→재상신(삭제 아님)은 무영향 — resubmitSettlement 는 같은 ref 로 재상신해 '이전 회차' 이력을 유지한다.
