# 릴리스 노트 — portal-web v1.5.255

결재 승인/반려 시 참조 업무 상태 전파(폐쇄 루프 1)를 **컴파일 타임에 강제**하도록 리팩터링했다. 결재 문서
유형과 그 전파 핸들러의 대응을 타입 시스템이 전수 요구해, 유형을 늘리면 전파 누락이 빌드 에러로 잡힌다.
직전 v1.5.253(상신취소 복원 강제)과 동일 패턴을, 지급·SR완료를 좌우하는 더 높은 위험도의 승인 경로에 확장.
동작은 불변(순수 구조 개선).

## 배경 — 발견 경위

v1.5.253(회수 복원 컴파일 강제)의 자매 경로인 승인/반려 전파를 대조하다, `decide()` 의 유형별 전파 `if`
블록이 12개 결재 유형과 **수동으로만** 짝지어져 있음을 확인했다. 12종 중 11종은 전파 블록이 있고, `'부서서약
현황 상신'`만 전파가 없다 — 이는 결함이 아니라 의도된 무상태 스냅샷(부서 서약 현황은 재직자 서명에서
파생되는 스냅샷이라 승인 시 되돌릴 백킹 엔티티가 없다)이다. 그러나 그 no-op 이 **암묵적**(블록 부재)이라
감사 시 '전파 누락'으로 오인되기 쉽고, 향후 백킹 엔티티가 있는 결재 유형을 추가하며 전파 블록을 빠뜨리면
컴파일러가 못 잡아 승인됐는데 참조 업무가 '결재중'에 갇히는 고아 in-flight 가 될 수 있었다.

## 주요 변경
- `lib/approvals.ts` `APPROVAL_PROPAGATORS: Record<ApprovalDocType, (s, ref, verdict) => void>` 신설 —
  승인/반려 전파의 단일 원천. `Record` 키가 `ApprovalDocType` 전체를 요구하므로 유형 추가 시 전파 핸들러
  누락이 컴파일 에러(TS2741). 각 핸들러는 진행중 상태(예: settlement '결재중')일 때만 전파(중복·경합 방어).
  `'부서서약 현황 상신'`은 명시적 no-op 핸들러 + 주석으로 스냅샷 의도를 문서화(암묵 부재 → 명시 의도).
  정산품의(투자·비용)는 동일 핸들러 공유.
- `app/(app)/work/approvals/actions.ts` `decide`: 12종 인라인 전파 `if` 블록을 맵 단일 디스패치
  (`if (ap.ref) APPROVAL_PROPAGATORS[ap.docType](s, ap.ref, verdict)`)로 대체. 문서 유형 상호배타라 등가.
  더는 쓰지 않는 `ACCOUNTS` import 제거(전파 핸들러가 lib 로 이동).

## 호환성·영향
- 무동작변경: 12종 전 결재 유형의 승인/반려 전파(지급완료·CI배정·SR완료 전파·장애/출력물/서약 배치 전파·
  위반/점검 전이)는 종전과 동일. 문서 유형별 블록이 상호배타라 인라인 분기와 맵 디스패치가 등가(호출당
  정확히 하나). 순수 구조 개선이라 런타임 동작·데이터·화면 불변.
- 향후 결재 유형 추가 시, 전파 핸들러(또는 명시적 no-op)를 함께 넣지 않으면 `next build` 가 실패한다(의도된 강제).

## 검증
- 게이트 전량 그린: build · smoke · a11y · emptystate/corrupt · keycheck · health · e2e 96.
- 타입 강제 실증(fails-without-fix): `APPROVAL_PROPAGATORS` 에서 한 유형('보안위반 확인서')의 전파 핸들러를
  제거하면 `tsc --noEmit` 가 `error TS2741: Property '"보안위반 확인서"' is missing … Record<ApprovalDocType, …>`
  로 실패함을 실측(TSC exit 2), 복원 후 exit 0.
- 동작 파리티: e2e `sr`(CI배정 전파+할일)·`settle`(지급완료)·`devchain`(적용요청+변경 2단+SR완료 캐스케이드)·
  `withdraw` 등 전 결재 흐름 통과로 리팩터 전후 동일 동작 확인.
