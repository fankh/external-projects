# 릴리스 노트 — portal-web v1.5.211

인프라 변경관리의 **원복계획(rollback plan)**을 작업계획과 별개의 필수 산출물로 분리했다. 요구사항
(sample.xlsx·제품안내서 III장)은 "작업계획, 원복계획 필요"로 둘을 구분해 요구하나, 기존에는 단일 입력에
"작업계획 · 원복계획"으로 뭉뚱그려 담고 있었다.

## 배경 — 요구사항 대비 갭

sample.xlsx 인프라 변경관리는 "인프라 변경 내용 상세 작성, 작업계획, 원복계획 필요"를 명시한다. 감사 결과:
- `ChangeWork` 모델에 계획 필드가 `plan` 하나뿐이었고(`lib/types.ts`), 등록 폼도 단일 입력의 placeholder 를
  "작업계획 · 원복계획"으로만 표기해 두 산출물을 한 500자 필드에 뭉쳐 받았다.
- 목록·엑셀 어디에도 원복계획이 작업계획과 구분되어 드러나지 않았다 — 변경 실패 시 되돌림 절차가
  독립 산출물로 관리되지 않는 깊이 갭.

## 주요 변경

### 원복계획 별개 필드 (`lib/types.ts`, `lib/store.ts`)
`ChangeWork` 에 `rollbackPlan?: string`(플랫 필드)을 더해 작업계획(`plan`)과 분리했다. 시드 변경도
작업계획·원복계획을 각각의 필드로 나눴다.

### 등록·표시 분리 (`app/(app)/infra/changes/page.tsx`)
- 인프라변경 등록 폼을 작업계획·원복계획 두 입력으로 분리(둘 다 필수 — 요구사항 "원복계획 필요").
- 변경 작업 목록에 '작업 · 원복계획' 열을 더해 두 계획을 별개로 표시(원복계획은 ↩ 표기로 구분).

### 엑셀 export (`app/api/export/route.ts`)
변경 export 에 '원복계획' 열을 추가(작업계획과 별개 컬럼).

## 호환성·영향
- 무회귀: rollbackPlan 은 선택 필드(기존 데이터·시스템개발 변경은 미보유 시 미표시). 신규 인프라변경 등록만
  원복계획 필수. 플랫 문자열이라 스토어 손상 가드에 안전.
- 시스템개발 변경(SR 편입)은 작업계획만 자동 세팅되며 원복계획은 선택(운영계 반영 절차 특성).

## 검증
- 게이트 전량 그린: build · smoke · a11y · emptystate/corrupt · keycheck · health · **e2e 83**.
- e2e `sc_infra_rollback_plan`: 격리 데이터 파일의 기존 변경(원복계획 보유)이 작업계획과 별개로 표시됨을
  확인하고, 폼으로 작업계획·원복계획을 별개 입력해 등록한 신규 변경도 두 계획이 구분 저장·표시됨을 검증한다.
  수정 전(원복 미표시) 코드에선 두 단언이 모두 실패함을 대조 확인(테스트 유효성) 후 복원했다.
